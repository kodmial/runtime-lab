# Render lifecycle — current knowledge

## Confirmed
- Ephemeral workers are named `runtime-lab-issue<ISSUE>-<RUN_OR_ATTEMPT>`. `runtime-lab-controller` is persistent and must never be treated as an ephemeral worker.
- One issue attempt creates at most one worker. Model fallback reuses the same worker.
- Once a service ID exists, cleanup is mandatory on every terminal path. Deletion is primary; suspension is only an emergency fallback while deletion retries continue.
- Success requires authoritative absence verification (404/410 or equivalent). Unverified cleanup blocks GitHub write-back/materialization.
- Render workspace/list-owner responses expose the workspace identifier under `owner.id`; top-level `id` must not be assumed. Evidence: `../experiments/issue-9-run-36379129913.md`.
- Runner jobs may legitimately take up to 45 minutes; the controller polling envelope must exceed that bound plus margin. A 20-minute envelope caused a false timeout. Evidence: `../experiments/issue-9-run-36399649036.md`.

- Runner jobs live in worker process memory, so a worker restart turns a submitted job id into a permanent unknown-job 404. The controller poll loop must classify each poll from (HTTP status + parsed status): only queued/running on HTTP 2xx is pending; persistent 404/410 fails fast as job loss; transport failures retry within budget with periodic /health re-probes and diagnostic errors. Empty poll responses must never be treated as proof the job is still working. A single failed /health probe after a handful of transport errors is only a transient restart down-window (proxy 502s plus booting replacement): fail fast on transport errors only after three consecutive failed probes (15 consecutive transport errors, ~5 minutes); any healthy probe or any poll that reaches the worker resets the streak. Evidence: `../experiments/issue-31-run-36408413138.md`, `../experiments/issue-62-run-36432233858.md`.

- Render may restart a Free web service at any time (vendor contract: `https://render.com/docs/free`, re-verified 2026-09-28: anytime restart, ephemeral filesystem lost on restart, 0.1 CPU / 512 MB), so transient restarts must not fail the whole attempt: on job loss with a healthy runner the controller resubmits the identical payload on the SAME worker (never a second service) while poll iterations remain -- budget-limited, not count-limited. Fixed resubmission counts were falsified one live failure at a time (1 -> 2 -> 3 -> 4 -> 5, then run 36434278632 lost six consecutive jobs to six proven restarts inside the budget), so the count no longer gates recovery; only an exhausted poll budget stops retries. A proven same-process loss (healthy worker no longer knows the job it accepted -- an unknown-job 404 proves the poll reached the worker) is deterministic and fails fast immediately without burning budget. Restart evidence prefers the runner process instance id, then wall-clock-vs-uptime drift; uptime order alone is never proof of identity. Evidence: `../experiments/issue-33-run-36409578168.md`, `../experiments/issue-41-run-36416327622.md`, `../experiments/issue-47-run-36419944182.md`, `../experiments/issue-53-run-36424221297.md`, `../experiments/issue-60-run-36429560757.md`, `../experiments/issue-62-run-36432233858.md`, `../experiments/issue-68-run-36436736447.md`.

- A memory-pressure restart storm abandons resubmission instead of burning the budget (run `36439192645`: seven proven restart-losses were all resubmitted under the budget-limited policy, then the eighth `running` job starved when the shared 140-poll budget ran out -- a budget sized for ONE 45-minute execution can never cover K full executions, so every resubmission also shrinks the next attempt's window; cgroup pinned at 512 MB with +430,890 max-stall growth while the ~600 MB agent cannot fit the Free worker). The breaker fires only when BOTH hold: a streak of consecutive proven-restart losses at the lifecycle threshold (pending polls do not reset it; model fallback does) AND live telemetry proving memory pressure (usage pinned at the cgroup limit plus repeated replacements or a same-instance stall surge; per-container counters reset on replacement, so surges are measured within same-instance groups, and telemetry gaps fail open toward resubmission). Storm evidence is gap-tolerant: sampler gaps (ok=false during restart down-windows) and harness event markers separate every live replacement, so they are skipped with continuity preserved and groups reset only on instance change (run `36442675039` lost ten jobs with 2103 ok / 2590 samples and +129,597 max growth while a gap-resetting detector reported zero transitions). Without pressure evidence the streak alone never abandons, so transient host-restart clusters keep budget-limited recovery. Evidence: `../experiments/issue-71-run-36445119082.md`, `../experiments/issue-73-run-36448373714.md`.

- Storm verdicts are auditable from the durable record: the memory summary embeds the deciding inputs (pinned ratio, transition count, within-group surge) with their thresholds, the deciding branch (`replacements`/`stall_surge`/`none`), and the boolean verdict, and the storm diagnostic carries the same fields; the shell-resolved streak threshold is honored by the decision helper (a corrupt threshold fails open toward resubmission). The replacements branch is live-validated by run `36493316814` (four proven restarts, usage pinned at 99.997% of the 512 MB limit, within-group surge 448 vs the 10000 threshold, global first/last event deltas 0): quiet stall counters do not exonerate a pinned replacement storm. A second live shape (run `36493364897`: ratio exactly 1.0, surge 162, same 4-restart/5-instance cadence) independently confirms the pure-replacements path. Evidence: `../experiments/issue-113-run-36494567244.md`, `../experiments/issue-112-run-36495903902.md`.
- The poll-loop envelope honors the shell-resolved `POLL_MAX_ATTEMPTS` / `POLL_INTERVAL_SECONDS` (validated numeric, lifecycle defaults 140/20 on corrupt values) in the loop bound, terminal-iteration checks, and poll sleeps; `POLL_UNKNOWN_THRESHOLD` carries the same numeric fallback. A resolved lifecycle value and its use must never silently diverge. Evidence: `../experiments/issue-112-run-36495903902.md`.

- Every runner process owns a unique `instance_id` (uuid at manager startup) exposed in `GET /health` alongside `pid`, `started_at`, `uptime_seconds`, and lightweight resource signals, and stamped into each submitted job's metadata/status. A changed instance id across a job loss proves a restart/replacement directly, even when the new uptime is numerically greater than the old snapshot (run `36410676408` advanced minutes of wall-clock with only `25.9 -> 48.9 -> 60.3` uptime deltas, which the old `current < prior` check misread as "same worker process lifetime"). OpenCode CLI provisioning is serialized behind an install lock so concurrent jobs never run concurrent heavyweight installers on the small free worker. Evidence: `../experiments/issue-41-run-36416327622.md`.

- Worker memory budget (measured, issue #52): the pinned standalone OpenCode binary (1.18.33, ELF x86-64, libc-only, ~177 MB on disk) peaks at ~177-200 MB for `--version` and ~600-615 MB for a real free-model agent run (full process-tree polling, max family 1-2, no hidden helpers). The Python controller idles at ~22 MB (~4% of peak), so its overhead is negligible and no Go rewrite is justified; npm/bun/pnpm/yarn forms are downloader shims for the same binary and only add a runtime process (~19 MB for node). Under Docker `--memory=512m --memory-swap=512m`, `--version` passes, a 700 MB hog OOMs as expected, and the real agent is nondeterministic at the boundary (one trial OOM-killed exit 137, another throttled through with `max 140` events). Reliable envelope is ~730 MB (peak + 128 MB headroom); 512 MB Free cannot reliably host real agent work and swap must not be assumed (swap masked ~52 MB when allowed). Evidence: `../experiments/issue-52-run-36423884312.md`, `automation/benchmark-results/memory-benchmark-issue-52.md`, rerunnable via `python3 automation/memory_benchmark.py --include-network`.
- Deterministic OpenCode provisioning (issue #52): the build copies the pinned binary to repo-relative `.opencode-bin/opencode` (never rely on build-time HOME equaling runtime HOME); resolution order is explicit override > deploy artifact > PATH > HOME; production start command sets `RUNNER_ALLOW_RUNTIME_INSTALL=0` so jobs never run network installation and fail fast when the binary is absent; `/health` exposes `opencode_bin`/`opencode_version`/`allow_runtime_install` and reports 503 while not ready; startup logs the safe resolved path/version. Evidence: `../experiments/issue-52-run-36423884312.md`.
- Container memory telemetry (issue #57): the worker resolves its cgroup from `/proc/self/cgroup` (v2 entry first, v1 memory entry second, mount root last) and reports container limits/usage from cgroup files (`memory.max`/`memory.current`/`memory.peak`/swap/`memory.events`, v1 equivalents) in `GET /health` under `resources.cgroup`, separate from the Python process RSS/HWM; `max` and near-2^63 limits mean unlimited (None), and each missing file degrades only its own fields. The temporary Actions harness starts a bounded external sampler (`automation/render_memory_sampler.py`, ~1s, 2s max) after healthy / before submit, stores JSONL on the Actions side so pre-restart samples survive, marks resubmission/fallback transitions, and on every terminal path stops the sampler, logs/prints the summary, and merges it into the job result as `memory_telemetry`. Do not infer container memory from parent RSS alone. Live proof of driver (run `36430429432`): cgroup limit/current/peak all pinned at 512.0 MB with Python RSS only ~32 MB and `memory.events max` +434 while the ~600 MB agent ran, proving memory-pressure restarts rather than host maintenance. Evidence: `../experiments/issue-57-run-36428268037.md`, `../experiments/issue-62-run-36432233858.md`.
- Transparent disk-backed heap is not a path to 512 MB (measured, issue #56): libvmmalloc (source-built from `pmem/vmem`, no noble package), memkind 1.14 memtier FS_DAX tier, and a minimal custom MAP_SHARED shim all demonstrably move plain-malloc traffic to file-backed mappings, but the pinned OpenCode/Bun binary keeps ~440 MB of ~600 MB in direct anonymous mmap (`[anon:WKFastMalloc]` ~384-389 MB, `[anon:JSGigacage]`, `[anon:JSJITCode]`, `[anon:JSStructureHeap]`, unnamed anon; `[heap]` only ~40 kB) that bypasses libc malloc by design, so interposers move 0-1.4% and peak is unchanged. memkind memtier segfaults the Bun binary deterministically (exit -11); unprivileged userfaultfd returns EPERM with no maintained transparent wrapper; `BUN_OPTIONS=--smol` saves only ~40 MB. Under Docker 512 MB/no-swap every candidate still OOMs except boundary-luck passes. No allocator wrapper is wired into production; rerun `python3 automation/disk_heap_benchmark.py --include-network [--docker]` after any OpenCode re-pin. Evidence: `../experiments/issue-56-run-36429944096.md`, `automation/benchmark-results/disk-heap-issue-56.md`.

## Do not repeat
- Do not capture child output with unbounded `subprocess.run(PIPE, PIPE)` and truncate afterwards: retention is O(output) no matter how small the terminal limit is. Spool to files and read back only bounded head/tail slices (`automation/bounded_output.py:run_bounded`). Evidence: `../experiments/issue-80-run-36452901431.md`.
- Do not truncate terminal output head-only (`text[:limit]`): failures surface at the tail. Always keep head + tail with an explicit omission marker. Evidence: `../experiments/issue-80-run-36452901431.md`.
- Do not retain terminal job records/workspaces without a cap (`RUNNER_MAX_RETAINED_JOBS`, default 20); delete workspaces after lock release and await the eventual bounded state in tests. Evidence: `../experiments/issue-80-run-36452901431.md`.
- Do not scope per-job `OPENCODE_DB` inside the clone (`<workspace>/repo`): it pollutes `git status` change detection. Scope session isolation to the workspace root. Evidence: `../experiments/issue-80-run-36452901431.md`.
- Do not parse the first workspace as `.[0].id`.
- Do not use an outer poll timeout shorter than the runner timeout.
- Do not treat an empty/unparsable job poll as queued/running.
- Do not fail fast on transport errors after a single failed /health probe; require three consecutive failed probes (a lone failed probe is a restart down-window).
- Do not create a second service for model fallback or polling retry (same-worker resubmission reuses the existing worker while poll budget remains; a fixed resubmission count must not gate recovery).
- Do not gate storm abandonment on a bare resubmission count; require live memory-pressure evidence alongside the streak, or transient clusters lose their budget-limited recovery.
- Do not adjudicate a storm from global first/last memory-event deltas alone: per-container counters reset on every replacement, so those deltas read ~0 even mid-storm; consult the embedded memory-pressure verdict block (pinned ratio, transitions, within-group surge, deciding branch). Evidence: `../experiments/issue-113-run-36494567244.md`.
- Do not duplicate lifecycle constants as shell literals in the poll loop: resolve `POLL_MAX_ATTEMPTS` / `POLL_INTERVAL_SECONDS` (plus every threshold) from `render_lifecycle`, validate numeric with lifecycle defaults, and honor the resolved values in the bound, guards, and sleeps. Envelope tests must assert honoring, not literals. Evidence: `../experiments/issue-112-run-36495903902.md`.
- Do not infer worker process identity from `current_uptime < prior_uptime` alone; a replacement process can report a larger uptime than the old snapshot. Compare instance ids first, then wall-clock elapsed vs uptime delta.
- Do not provision workers with unpinned `curl -fsSL https://opencode.ai/install | bash`; always pin `--version` (or `$OPENCODE_VERSION`).
- Do not resolve the OpenCode binary from build-time `$HOME` alone; ship and resolve repo-relative `.opencode-bin/opencode`.
- Do not run network installation inside a production job (`RUNNER_ALLOW_RUNTIME_INSTALL=0`); fail readiness fast instead.
- Do not rewrite the Python controller in another language for memory reasons: measured overhead is ~22 MB vs a ~600 MB agent peak.
- Do not add an LD_PRELOAD allocator wrapper (libvmmalloc/memtier/custom shim) to production for the 512 MB worker: measured file-backed movement is 0-1.4% of the agent footprint and memtier segfaults the Bun binary.
- Do not duplicate OpenCode subprocess defaults outside `opencode_runner.default_opencode_env_overrides()`; apply them with setdefault semantics so operator overrides win. Evidence: `../experiments/issue-75-run-36628597460.md`.
- Do not add `--pure` to the production OpenCode argv to enable pure mode: pure mode arrives via `OPENCODE_PURE=1` in the canonical env overrides, so the `opencode run --auto --model` argv stays identical to the workflow step and to the `/proc` cmdline identity evidence. Evidence: `../experiments/issue-159-run-36631044430.md`.
- Do not treat permission-denied tool configuration as module exclusion for the lite variant: excluded subsystems must be absent from the lite static-import closure (including side-effect, dynamic, require, and re-export forms), validated per removal group.
- Do not substitute the baseline OpenCode binary for an issue that requires one exact GitHub Actions artifact (numeric id + source workflow run + sha256): fail closed before any worker exists instead of burning a storm-doomed run that never tests the required binary. Evidence: `../experiments/issue-115-run-36496877520.md`.
- Do not accept a PR #15 transport on binary-digest + numeric-shape match alone: artifact IDs are repo-scoped while delivery fetches only from `kodmial/opencode`, so require a pinned `(artifact_id, source_run_id, archive_sha256)` triple plus the `kodmial/opencode` repository declaration, or a foreign triple 404s after a wasted service creation. Evidence: `../experiments/issue-146-run-36629442621.md`.
- Do not drop the pre-creation refusal retirement signal when classifying qualification evidence: `record_render_qualification.classify` must propagate `permanent`/`superseded`/`successor` from the refusal record into the durable payload while keeping the fingerprint inputs frozen, so posted markers keep deduping identical redispatches. Evidence: `../experiments/issue-138-run-36505951306.md`.
- Do not rely on post-failure fingerprint dedup alone to stop retired-contract redispatch: smoke issues skip the qualification classifier (`not-chain`, empty fingerprint), so only a pre-dispatch body check (`superseded_dispatch_guard`, wired into `decide_eligible` after the priority gate) holds them paused instead of minting one more P0 repair per redispatch. Evidence: `../experiments/issue-154-run-36631020621.md`.
- Do not assume a guard stops redispatch unless a live path consults it: run `36632062583` executed at a base containing the #154 guard yet redispatched identically, because the scheduler envelope and repair-reset unpause never call `decide_eligible`. Name the hold at an owned production chokepoint (executor `held-superseded` verdict) so provisioned envelopes can key on it; do not add executor GitHub writes (read-only invariant) or tombstone holding issues (they would permanently disable future P0 repairs for the source). Evidence: `../experiments/issue-161-run-36632121093.md`.
- Do not leave a hold verdict log-only: run `36633812500` printed the `held-superseded` line yet its uploaded refusal record carried no hold marker, so durable-evidence consumers still had to scrape logs. Carry the verdict in the structured refusal record (`dispatch_hold` from the same registry) alongside the log line. Evidence: `../experiments/issue-165-run-36634422005.md`.
- Do not judge a file-backing experiment by file-backed bytes alone: MAP_PRIVATE file pages carry the same cgroup charge once dirtied, so only peak / `max`-event movement proves 512 MB fitness (~1.1 GB redirected with zero peak movement in issue #144). Evidence: `../experiments/issue-144-run-36509899175.md`.
- Do not remap Bun/JSC anonymous memory with MAP_SHARED file semantics: a fork child shares those pages with the parent (deterministic CoW break); the smallest safe design is MAP_PRIVATE file backing plus post-fork anonymous fallback. Evidence: `../experiments/issue-144-run-36509899175.md`.

## mmap file-backing probe for PR #15 (issue #144)

- Direct-anonymous-mmap interposition technically works but does not move
  the 512 MiB peak: an opt-in `LD_PRELOAD` shim
  (`automation/mmap_filebacked_shim/shim.c`, private-file mode,
  >= 1 MiB MAP_PRIVATE anon RW only, fail-closed) redirects ~1.1 GB per
  real-agent trial (~1000x the malloc-only libvmmalloc coverage) with zero
  behavioral regression, yet same-binary A/B peaks are unchanged
  (off 537,964,544/537,096,192 B vs on 537,149,440/545,255,424 B, all exit
  0, `2 passed`, `oom_kill` 0, both arms `marginal`). MAP_PRIVATE file
  pages carry the same cgroup charge once dirtied by the JSC GC; only
  MAP_SHARED writeback (rejected: deterministic fork-CoW break, locked by
  test) or real swap could reclaim them. Not wired into any delivery path.
  Contract: `automation/mmap_filebacked.py` + `automation/mmap_filebacked_bench.py`;
  tests: `automation/test_mmap_filebacked.py` (22 tests). Evidence:
  `../experiments/issue-144-run-36509899175.md`,
  `automation/benchmark-results/mmapfb-issue-144-run-36509899175.json`.
- Bun/Zig runtime constraints for any future interposer: most mmaps
  (incl. the 8 GiB Gigacage reservation) use raw syscalls invisible to
  `LD_PRELOAD` (`--version`: 42 strace mmaps vs 3 libc interceptions);
  raw exit skips destructors (telemetry needs periodic + synchronous
  flush to per-pid files); fork children must fall back to anonymous
  (`pthread_atfork`) to protect zero-init. Bun compiles are locally
  deterministic but not reproducible across build environments (identical
  source/command/toolchain, 4 KiB digest drift vs the #134 fingerprint),
  so pin binary identity per build. Sparse per-process 2 GiB pools cost
  ~72 KB actual disk for 35 GB apparent.
