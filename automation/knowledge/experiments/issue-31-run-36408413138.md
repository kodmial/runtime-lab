# Repair poll loop that masked job loss as "empty" timeout

## Hypothesis / objective
Repair the concrete defect that failed Render execution for source issue #9 in run 36402447309 (execute=failure, cleanup=success, smoke mode): the controller polled a runner job for the full ~47-minute budget and reported only `Runner job did not finish in time (last status 'empty')`, masking whether the job was lost, the runner was down, or the job was genuinely slow.

## Prior knowledge consulted
- `automation/knowledge/PROTOCOL.md` (READ -> PLAN -> EXECUTE -> RECORD -> PROMOTE).
- `automation/knowledge/topics/render-lifecycle.md` (one worker per attempt, 140x20s poll envelope from run 36399649036, in-process cleanup plus watchdog).
- `automation/knowledge/topics/agent-execution.md` and `scheduler-recovery.md` (repair must fix reusable implementation with regression coverage).
- `automation/knowledge/experiments/issue-9-run-36379129913.md` (owner.id contract) and `issue-9-run-36399649036.md` (20-minute envelope false timeout; budget raised to 140x20s).
- `automation/knowledge/experiments/issue-27-run-36405661952.md` and `issue-28-run-36405666089.md` (watchdog and fault matrix; this repair stays in the poll path, not cleanup).

## Preconditions / changed premise
Material premise changed since the run 36399649036 repair: the poll budget is now sufficient (140x20s covers the 45-minute runner timeout), so the run 36402447309 failure is a new defect at the same lifecycle boundary, not a repeat of the short-envelope experiment. No live Render credentials were used; the fix was developed and verified offline with contract-level fakes.

## Procedure
1. Inspected run 36402447309 via `gh run view 36402447309 --repo kodmial/runtime-lab --log`: service `srv-dat30u8473hc73ehe7v0` created, deploy `dep-dat30uo473hc73ehe9eg` live, runner healthy, job `395c56e052544734b030406fbfff1555` submitted at 09:17:44, then `did not finish in time (last status 'empty')` at 10:04:32. Cleanup verified deletion (HTTP 404).
2. Read `automation/render-job.sh` poll loop, `automation/render_lifecycle.py` poll constants, and `automation/runner_server.py` job-status contract (`GET /v1/jobs/{jobId}` returns 404 `{"error":"unknown job..."}` for unknown ids; jobs live in worker process memory with no durable state).
3. Verified the Render retrieve-service contract against current official vendor documentation (`https://api-docs.render.com/reference/retrieve-service`): 200 service object, 404/410 absence signals, 429 with Retry-After, 5xx transient errors. The repo's 404/410 deletion-verification usage matches the documented contract.
4. Added `classify_job_poll_response()` plus `JOB_POLL_UNKNOWN_JOB_THRESHOLD` (3) and `JOB_POLL_TRANSPORT_HEALTH_CHECK_EVERY` (5) to `automation/render_lifecycle.py`.
5. Rewrote the `automation/render-job.sh` poll loop to capture the HTTP status per attempt, classify each outcome, fail fast on persistent unknown-job 404/410 with a health-qualified diagnostic, re-probe `/health` on repeated transport failures, and report the last HTTP code plus consecutive-failure counts on terminal timeouts.
6. Added regression tests and ran the full offline suite.

## Observations
- The old poll loop used `curl -fsSL ... || true` and matched `queued|running|"")`, so every unparsable poll (unknown-job 404 collapsed by `curl -f`, 429/5xx, connection failure, empty body) became status `""` and was retried as "still working" for all 140 iterations.
- The runner's documented 404 `unknown job` answer and the in-memory-only job store mean a worker restart turns a submitted job id into a permanent 404 that can never become terminal; the old loop waited the full ~47 minutes anyway and then reported a generic timeout with no HTTP code, no failure count, and no runner-liveness signal.
- Cleanup in the failed run worked correctly (delete plus 404 verification); the defect is confined to the job-result polling path.

## Interpretation
The worker was never proven hung: `last status 'empty'` is not evidence of a slow job, it is evidence the polling layer discarded the distinguishing signal (HTTP status) and treated absence-of-answer as presence-of-work. The reusable fix is outcome classification at the poll site, not a longer timeout.

## Decision / result
- `automation/render_lifecycle.py`: new pure helpers `classify_job_poll_response()`, `should_fail_fast_on_unknown_job()`, `should_probe_runner_health()` with thresholds `JOB_POLL_UNKNOWN_JOB_THRESHOLD = 3` and `JOB_POLL_TRANSPORT_HEALTH_CHECK_EVERY = 5`.
- `automation/render-job.sh`: poll loop now records the HTTP code per attempt, classifies via the helper, resets counters on pending/terminal/fallback-submit states, fails fast with `Runner no longer knows job <id> (HTTP <code>, N consecutive polls; runner health: ...)` on persistent unknown-job, fails fast when transport failures coincide with a failing `/health` probe, and otherwise retries within the unchanged 140x20s budget with diagnostic terminal errors.
- Poll budget, one-service-per-attempt invariant, same-worker model fallback, and mandatory cleanup are unchanged.

## Reusable knowledge
- An empty poll response is absence of evidence, never evidence the job is still working: always classify polls from (HTTP status + parsed status), track consecutive unknown/transport outcomes separately, and fail fast on provable job loss.
- In-memory job stores plus restartable free-tier workers imply poll targets can disappear permanently; the poller must distinguish "job gone" (404) from "answer lost in transit" (transport error) with different policies.
- Terminal timeout errors must carry the last HTTP code, the last parsed status, and consecutive-failure counts, or the next repair loop has nothing to investigate.

## Unresolved questions / next experiment
- The actual worker-side fate of job `395c56e052544734b030406fbfff1555` (slow OpenCode task vs worker restart vs network partition) cannot be determined post hoc because the ephemeral service was deleted and the old poller kept no per-attempt diagnostics; the next live smoke with the new poller will produce a discriminating error if the failure recurs.
- Consider persisting per-poll attempt diagnostics (HTTP codes) to the result/state file so future repairs have a timeline even when the worker is gone.
