# Provider fleet control plane with Render node rotation

## Interpretation

Single-flight per-pool locks plus expected-generation preconditions convert concurrent 307 reports into exactly one provisioning: the winner publishes generation N+1 atomically after readiness, and losers serialized after publication observe the current route (409 with generation N+1) instead of provisioning again. Bounded attempts plus the per-pool rotation window keep repeated rotations from becoming a Render-service storm, while failure paths restore the prior active record so a failed rotation never unpublishes a working node. The file store keeps one active route/generation per pool durable across restarts, and the store/provisioner seams allow a Redis backend later without changing the contract. Stripping LLM fields at the body boundary and projecting only safe metadata into responses keeps prompts/completions out of the controller.

## Reusable knowledge

- Provider fleet rotation belongs in the persistent controller process as a separate control module, never in the ephemeral worker: per-pool locks give single-flight rotation, expected-generation preconditions reject stale duplicates, and readiness-before-publication plus post-publish retirement keep the route atomic.
- Bound rotation storms with two envelopes: max provisioning attempts per rotation plus max rotations per pool per window (429 with the current route preserved).
- At HTTP/parse boundaries, compare cross-imported exception types by name when both top-level and `automation.*` import paths exist (no package `__init__`); otherwise allow-list rejections misreport as 503.

## Unresolved questions / next experiment

- Live Render provider-node provisioning parameters (long-lived provider service shape vs ephemeral worker payload) still need a live proof run against the vendor API before Continuum integration.

- Continuum client behavior on 409-with-current-route (re-resolve vs retry) belongs to Continuum issue #31, not this repo.
