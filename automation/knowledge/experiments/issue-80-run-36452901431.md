# Bound OpenCode session history and tool-output memory for one-shot jobs

## Hypothesis / objective

Transient worker memory spikes from large session history, shell/test
output, tool results, and stale task state can be eliminated with
configured bounds — fresh OpenCode process/session per issue, bounded
streaming/spooling capture with head/tail diagnostics, and bounded
history retention — without changing provider semantics or hiding
critical errors.

## Observations

- Old runner capture retained full multi-MB strings in memory before
  truncating; `_truncate` was head-only (hid trailing errors);
  `_jobs` never evicted (records + workspace clones accumulated).
- Fork shell/grep/glob/read paths are already bounded; the Task-tool
  subagent path injects full transcripts into the parent session with
  no truncation call.
- Measurements (runner side, A/B): single ~2.0 MB log 1,988,895 B ->
  32,822 B retained (0.017); tracemalloc Python-side peak 9,946 KB ->
  394 KB (0.040); 20x repeated calls 11.78 MB -> 0.66 MB (0.056);
  all tails preserved; spooling time overhead within noise.
- Checks: 101/101 tests pass (`test_bounded_output`,
  `test_opencode_runner`, `test_runner_server`,
  `test_opencode_provisioning`, `test_opencode_fork`,
  `test_opencode_headless_inventory`); `knowledge_catalog.py
  validate` ok (27 records pre-write); `py_compile` clean.

  tests, and this record; no `.github/workflows/**` changes; no git
  commits/pushes/branch operations (workflow owns Git state).

## Interpretation

The runner side of the Definition of Done is met: no single tool
call or accumulated output on the worker can grow memory past the
configured bounds, diagnostics keep head context plus the error tail
with explicit omission markers, and sessions start fresh per issue.
The remaining unbounded path is inside the fork binary (Task-tool
subagent injection), which this run specifies precisely but cannot
land itself: fork PR/branch orchestration belongs to the workflow,
and #79 has no landed revision to build on yet.

## Reusable knowledge

- Runner capture must be file-backed (`run_bounded` spool pattern):
  PIPE-then-truncate is O(output) memory no matter how small the
  terminal limit is.
- Terminal summaries must be head+tail with an omission marker, never
  head-only: failures surface at the tail.
- Per-job `OPENCODE_DB` must resolve outside the clone
  (`_session_scope_dir`): the OpenCode pipeline runs inside
  `<workspace>/repo`, and a DB inside it would pollute `git status`
  change detection.
- Retention caps must delete workspaces after lock release and tests
  must await the eventual bounded state (async cleanup race).
- Fork `Truncate` service shape for future work: `tool_output`
  config (`max_lines` 2000 / `max_bytes` 50 KB defaults),
  `direction: "tail"` supported, `Full output saved to:` retrieval,
  7-day hourly GC.
