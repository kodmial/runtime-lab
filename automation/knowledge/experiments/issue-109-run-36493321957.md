## Interpretation

- The artifact-integrity half of the issue is fully satisfied: exact artifact ID from the exact source run was downloaded (cross-repo works with the workflow token), both checksum links verified, and the executed binary SHA-256 is fingerprinted. No substitution occurred.
- The memory-qualification half is blocked by a fork build defect, not by memory pressure: the unstamped `0.0.0` version trips the free-tier minimum-version gate, so no trial ever reaches search/edit/shell/test. All three trials fail identically with zero `max`/`oom_kill` events and peaks comfortably under the ceiling, which proves the envelope is not the cause and forbids both a fit claim (nothing completed) and a does-not-fit-memory claim (no pressure signal).
- The ~422 MiB Docker peaks and the ~503 MiB host peak must never be read as memory-fit evidence: they measure a 3-second fast-fail handshake, not the required workload (same artifact class as the rejected ~219 MB claim in issue #78). - The defect is small and fork-local (stamp `OPENCODE_VERSION`/fetch tags in the artifact workflow, mirroring the `OPENCODE_VERSION=1.18.33 OPENCODE_CHANNEL=latest` precedent from issue #105), but landing it belongs to the fork pipeline on a new head SHA plus a rebuilt artifact; this run performs no pushes and records the fix location rather than landing it.

## Decision / result

Outcome `failed` (definitive negative qualification, not missing evidence):

- **Blocked (provider version gate)** — the exact artifact `11001896223` (binary SHA-256 `a6dabf731c49999d5c95dd7477cd74f18070615f6a01a8ce36cd8e35b5dce38d`) executes under verified 512 MiB/no-swap but cannot perform the required real coding workload on the required anonymous path: all three real-agent trials exit 1 with `OpenCode 1.18.0 or newer is required to use the free tier`, no file edited, no test run. This maps to none of the issue's memory classes cleanly: not reliable/marginal (nothing completed), not does-not-fit-memory (zero pressure signals; failure not attributable to the envelope), not infrastructure-blocked-download (artifact downloaded, verified, started, telemetry captured). It is a fork build defect (unstamped `0.0.0` version), and no 512 MiB memory verdict for this artifact line is possible until the fork ships a version-stamped rebuild.
- Deliverables: exact artifact ID + source SHA + executed binary SHA-256 above; Actions run `https://github.com/kodmial/runtime-lab/actions/runs/36493321957`; reproducible contract in `automation/opencode_max_headless_qualify.py` (13 tests); machine-readable evidence in `automation/benchmark-results/max-headless-issue-109-run-36493321957.json`; trial-by-trial peaks/events/correctness in Observations.

## Reusable knowledge

- Always check `--version` output of a fork artifact before burning agent-trial time: an unstamped `0.0.0` build is rejected by the free-tier console gate before any tool runs, and its fast-fail peak is not memory evidence.
- The artifact workflow for PR-built binaries must stamp the version (`OPENCODE_VERSION` env and/or tag fetching) exactly like release builds do; `Script.version` from `@opencode-ai/script` falls back to `0.0.0` on tag-less PR checkouts.
- A provider version gate surfaces as `agent_exit=1` with zero `max`/`oom_kill` events and a sub-ceiling peak plus an explicit stderr shape; record the stderr shape so future agents can distinguish it from OOM/throttle without re-running.
- Cross-repository `actions/artifacts/<id>/zip` download with the workflow token works for `kodmial/opencode` artifacts and the archive digest in the issue spec verifies byte-for-byte; keep verifying both links (archive digest, then bundled `.sha256`).
