# Name the retired-contract hold at the executor choke point (repair run 36632062583)

## Preconditions / changed premise

Material premise vs the #154 repair (run 36629441608 at base `3471ceb`):
the failed run 36632062583 executed at base `49a985b`, which already
contains the #154 `superseded_dispatch_guard` plus the `decide_eligible`
wiring, yet the retired #106 body redispatched and refused byte-identically
while minting repair #161. This falsifies the hypothesis that declaring the
body ineligible in `decide_eligible` stops the loop: no production caller
consults `decide_eligible` on the live `actions` backend. The scheduler
(`issue-scheduler.yml`, inline JS, no checkout) dispatches on
paused/active/blocker/priority labels only, and auto-merge unpauses the
source unconditionally on every repair merge (`repair-reset`), resetting
the dispatch-attempt counter -- so each repair merge re-arms exactly one
wasted run plus one new P0 repair (five repairs for #106 so far: #113,
#115, #118, #154, #161). Per protocol this repair does not repeat the live
Render experiment; it names the hold at the one production chokepoint this
repository owns (the executor) and locks it with regression tests. Source
issue #106 was not closed or modified. This run creates no Render service
(no executor envelope here by design).

## Interpretation

- The execute=failure outcome for run 36632062583 is the executor gate
  working correctly at HEAD, not a lifecycle defect: no worker could
  honestly test what #106 requires, so refusing pre-creation in seconds
  at zero cost is the only honest behavior.
- The reusable defect is enforcement-side: the retirement signal exists
  in the refusal record (`permanent`/`superseded`/`successor` per #125),
  in the durable qualification payload, and in `decide_eligible` (per
  #154), but no live `actions`-backend path consults any of them for a
  smoke issue -- so the finalize envelope keeps minting repairs and the
  repair-reset keeps re-arming dispatch. The executor is the only
  production chokepoint this repository can change without touching
  workflow envelopes, so the hold verdict is now named there in one
  stable machine-greppable line (`held-superseded`) that provisioned
  envelopes can key on to skip repair minting for identically-refusing
  contracts.
- The hold check is deliberately advisory and read-only: it never changes
  the verdict (the exact gate still refuses), never writes to GitHub
  (header invariant preserved), and an unparsable body means "no hold".

## Reusable knowledge

- A correct guard in an unconsumed mirror stops nothing: run 36632062583
  executed at a base containing the #154 `decide_eligible` guard yet
  redispatched identically, because the live scheduler and repair-reset
  paths never call it. Retirement checks must be enforced at production
  chokepoints, not only mirrored in controller helpers.
- When the only owned chokepoint is read-only (executor), name the hold
  verdict in one stable machine-greppable line without changing the
  verdict or adding writes: provisioned envelopes can then key repair
  minting and unpause decisions on it.
- Tombstone holding issues and executor-side issue writes were considered
  and rejected: the former would permanently disable future P0 repairs
  for the source, the latter violates the executor read-only invariant.
