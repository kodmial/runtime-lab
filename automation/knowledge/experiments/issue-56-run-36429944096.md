# Test transparent disk-backed heap for OpenCode under 512 MB

## Hypothesis / objective

A transparent user-space file-backed heap (LD_PRELOAD malloc interposer
with MAP_SHARED pool files on ordinary disk) can move enough of the pinned
OpenCode 1.18.33 agent footprint out of anonymous RAM to convert the
512 MB/no-swap workload from unreliable/OOM (issue #52: ~600-615 MB peak,
one OOM-kill, one throttled pass) into repeatable success, without kernel
swap or privileges. Success evidence: real agent runs under
512 MB/swap.max=0 with smaps proving anonymous-to-file-backed movement,
material peak reduction, and repeatable exit 0.

## Procedure

   package; PMDK 1.13 dropped it). `make -C src` succeeds; nondebug
   `libvmmalloc.so.1` used for measurement.
2. Verified each interposer on a trivial malloc-heavy binary with smaps:
   libvmmalloc, memkind memtier FS_DAX tier, and a new minimal shim
   (`automation/disk_heap_shim/shim.c`, `-Wall -Werror` clean,
   stress-tested incl. threads/aligned/foreign pointers) all move plain
   malloc traffic to `rw-s` MAP_SHARED unlinked pool files (32-131 MB
   file-backed for 32-128 MB mallocs).
3. Added `automation/disk_heap_snap.py` (tree-RSS peak, smaps
   anon/file/heap/deleted/pool classification, top anonymous mappings,
   cgroup peak/events/swap) and `automation/disk_heap_benchmark.py`
   (7 modes x host + Docker-512 matrix, hi + coding tasks), plus
   `automation/disk_heap_bench.Dockerfile` (ubuntu:24.04 to match the
   host glibc 2.39; ubuntu:22.04's glibc 2.35 cannot load the shims) and
   `automation/test_disk_heap.py` (12 offline tests).
4. Ran the full matrix with real network-backed agent runs: 7 host modes,
   12 Docker 512 MB/no-swap runs (hi + calc.py-bugfix coding task),
   capturing exit/OOM class, cgroup peak/events, swap.current==0, wall
   time, live smaps, and pool residency. memtier crash repeated 3x;
   userfaultfd probed via raw syscall (EPERM).
5. Merged artifacts to

## Observations

- Host (no limit): baseline exit 0, 5.3 s, 558-603 MB peak (440 MB anon);
  smol 552-562 MB; vmmalloc exit 0, no slowdown, pool 2.7 MB (0.5%);
  shim exit 0, pool 0.1-0.8 MB (<0.2%); memtier exit -11 SIGSEGV after a
  deterministic ~32 s stall, 3/3 hi runs (2 host + 1 container).
- Docker 512 MB/no-swap: baseline 0/2 OOM; smol 1/2 (one throttled pass
  at ceiling); vmmalloc 0/2 OOM (pool ~1.1 MB); vmmalloc+smol 1/2;
  shim 1/2 (one pass at 482 MB cgroup with 0.1 MB pool); memtier 0/2
  (1 SEGV + 1 OOM). Occasional passes sit at/just under the ceiling with
  ~0 MB pooled: boundary nondeterminism per issue #52, not allocator
  effect. swap.current stayed 0 in all no-swap runs.
- Live smaps names the irreducible heap: `[anon:WKFastMalloc]` ~384-389
  MB, unnamed anonymous ~34-39 MB, `[anon:JSGigacage]` ~13 MB,
  `[anon:JSJITCode]` ~8 MB, `[anon:JSStructureHeap]` ~7 MB, `[heap]`
  36-44 kB. The Bun binary exports no malloc-family symbols (`nm -D`),
  so interposers win lookup and the ~0% result is genuine: JSC/Bun
  allocate via direct anonymous mmap.
- userfaultfd syscall as unprivileged user returns EPERM
  (`vm.unprivileged_userfaultfd=0`); no maintained transparent wrapper
  for unmodified Bun/JSC exists, so no pager was built.
- Full offline suite: 354 passed (341 pre-existing + 13 new); catalog
  validates; no `.github/workflows/**` touched; no commits made.

## Interpretation

- The interposition mechanism itself works on ordinary disk (all three
  shims proven with 32-131 MB file-backed pools on trivial binaries),
  but OpenCode/Bun sends ~0% of its footprint through libc malloc-family
  paths after startup, so there is nothing to move.
- memkind memtier's transparent mode is real but incompatible with the
  Bun binary (deterministic SIGSEGV, likely allocator-runtime conflict).
- File-backed MAP_SHARED is not swap: only <1% of pages are even
  eligible, and dirty JSC pages would still carry the same cgroup charge
  until written back. Reclaim behavior under pressure is moot.
- The ~40 MB `--smol` saving is real but an order of magnitude short.

## Decision / result

- Verdicts: libvmmalloc partially works / not useful; memtier
  incompatible; custom shim partially works / not useful (probe only,
  never ship); --smol minor help; userfaultfd unsuitable; overall no
  candidate converts 512 MB/no-swap to repeatable success.
- No production wrapper implemented: deliverable 4's precondition (one
  approach clearly works and is maintainable) not met. Irreducible set
  identified as the named JSC/Bun anonymous mappings above.

## Reusable knowledge

- Measure interception at the smaps level per mapping (`[anon:*]`
  names), never assume LD_PRELOAD covers a Bun/JSC heap; `[heap]` near
  zero plus ~99% direct-mmap anon is the signature of an
  uninterposable heap.
- `nm -D <binary> | grep malloc`: no exported malloc-family symbols
  means interposers win lookup, so a ~0 MB pool result is genuine
  non-use, not shadowing.
- Container images for LD_PRELOAD stress must match (or exceed) the
  build host's glibc, else the loader fails before main
  (`GLIBC_2.38 not found` on ubuntu:22.04 vs noble-built shims).
- memkind >= 1.12 `libmemtier.so` is a genuine transparent LD_PRELOAD
  file-tier path for ordinary binaries (FS_DAX works on non-DAX
  filesystems); test Bun-family binaries for the SIGSEGV class before
  trusting it.
- Unlinked pool files still count as file-backed in smaps (watch for
  the `(deleted)` suffix when classifying; they remain page-cache
  backed).

## Unresolved questions / next experiment

- Whether a future OpenCode/Bun (or JSC `MallocProvider` env switch, if

- Render-side cgroup accounting may differ slightly from Actions Docker;

- Larger Render plans remain the only measured reliable path (per #52
