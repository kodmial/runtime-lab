# Repair quadruple-restart job loss by allowing four same-worker resubmissions

## Hypothesis / objective

Repair the concrete defect that failed Render execution for source issue #9 in run 36425019190 (execute=failure, cleanup=success, smoke mode): the original runner job plus all three allowed same-worker resubmissions were lost to four consecutive proven worker restarts, so the attempt failed fast with `resubmissions used: 3/3` even though the worker was healthy throughout and the losses occurred inside the unchanged poll budget.

## Preconditions / changed premise

Material premise changed since the issue #53 repair: run 36425019190 was the first live run to exercise the three-resubmission path (base commit 499f6d3, the issue #53 repair itself) and lost ALL FOUR jobs on the same healthy service with direct instance-rotation proof (cf0ce0e1fd5b -> 3b567ebafa1a -> 57c5fc5fe6d1 -> e0e82704a45d -> 9838a60f9feb; uptimes 26.9 -> 53.0 -> 57.6 -> 61.7 -> 62.7), at ~24, ~6, ~3, and ~4 minutes after each submit. This falsifies "three resubmissions suffice" as a bound and answers the open question left by the issue #53 record: restart clusters of four occur. The fix targets the resubmission bound only; poll budget, one-service invariant, and mandatory cleanup are unchanged. Fully offline; no live Render credentials or service used. Source issue #9 was not closed or modified.

## Observations

- The failed run behaved exactly as designed by the previous repairs: correct fail-fast classification (3 consecutive 404s per loss), correct health qualification (healthy at every loss), correct restart proof (instance rotation on all four losses), correct three resubmissions, then fail-fast on the fourth consecutive loss. Classification, detection, and diagnostics are not the defect; the bound is.
- The four job lifetimes (~24 + ~6 + ~3 + ~4 minutes, ~37 minutes wall-clock including deploy/health) sit inside the unchanged 140x20s (46m40s) poll budget, so a fourth resubmission would still have had remaining budget to attempt completion.
- `render-job.sh` needed no logic change: the resubmission branch, counters, baseline carry-forward, in-flight (fallback-aware) payload tracking, and diagnostics are all parameterized by the lifecycle constant.

## Interpretation

Fail-fast plus three retries converts a triple-restart cluster into a recovery, but Free-worker restarts observably cluster in fours (four consecutive proven replacements in ~37 minutes). The reusable fix is a fourth bounded same-worker resubmission of the reproducible payload: quadruple-restart clusters become retries, a fifth consecutive loss still fails fast, and every existing invariant holds (one service per attempt, same-worker policy, unchanged 140-iteration budget, mandatory verified cleanup).

## Reusable knowledge

- On Free workers with anytime restarts and in-memory job stores, three retries are insufficient when restarts cluster in fours: allow four bounded same-worker resubmissions (five job attempts total) within the unchanged poll budget, and keep failing fast on the fifth consecutive loss.
- Parameterize retry branches by the lifecycle constant so a bound change needs no shell-logic edit and diagnostics stay consistent (`resubmissions used: X/N`).
- Shell/HTTP fakes for consecutive losses must rotate a fresh instance id per loss; reusing the last instance makes the final loss read as "same worker process lifetime" and weakens the regression.

## Unresolved questions / next experiment

- Whether four resubmissions suffice for even larger clusters (five or more consecutive restarts in one attempt); the resubmit counter plus instance-rotation evidence in the diagnostics will answer from live runs.
- The worker-side trigger for the four replacements (OOM/resource pressure vs host maintenance) remains unproven; the container memory telemetry from issue #57 (shipped after the failed run's base commit) plus the per-job identity from issue #41 are the discriminating instruments on the next live #9 attempt.
- The fixed resubmission bound keeps growing one live failure at a time (1 -> 2 -> 3 -> 4); if five-loss clusters are ever observed, consider budget-limited resubmission (retry while poll budget remains) or a durable out-of-process job store instead of another fixed-bound increment.
- Mirror loss handling into the persistent-controller path (`render_controller._poll_job_terminal`), which still has payload-only visibility; deliberately left out of this scoped repair as in prior runs.
