# Refuse silent wrong-binary substitution for exact-artifact Render runs

## Hypothesis / objective

Repair the concrete repository defect behind the Render execution failure for source issue #106 in run 36495681860 (execute=failure, cleanup=success, smoke mode): the worker lost four consecutive jobs to four proven restarts and storm-aborted at poll 38/140 -- but the storm verdict is a true positive, not the defect. The defect is that the run never tested what #106 requires: the exact GitHub Actions artifact (`opencode-coding-linux-x64` ID `11001896223` from workflow run `36492639568`, checksum-verified, no rebuild, no binary substitution). Success evidence: the root cause is identified from log evidence without guessing, both vendor contracts are re-verified against current official docs, the Render path fails closed before any worker exists when such a contract is unsatisfiable, regression tests reproduce the run's failure mode offline, and the offline suite plus catalog validation pass.

## Observations

- The failed run behaved exactly as designed up to the terminal error: correct fail-fast classification (3 consecutive unknown-job 404s per loss), healthy runner at every proven loss, instance-id-first restart proof on all four losses, three same-worker resubmissions, audited abandonment at the fourth proven loss (poll 38/140) instead of burning the budget.
- The storm verdict is a true positive: usage pinned at ratio 1.0000 with 4 instance transitions satisfies the replacements branch; the #113 diagnostic made that auditable in the durable log. Loosening the gate is excluded -- nothing in the repo adjudicates fast-kill OOM vs platform restarts after the fact, and the vendor contract documents anytime-restarts on a box the ~600 MB agent systematically does not fit.
- The executed binary was the baseline pinned binary, not the required exact artifact (deduced, not guessed): (a) no code path conveys a workflow artifact to the worker (payload, start command, and credentials all absent); (b) the issue-109 trials prove the exact `0.0.0` artifact fast-fails in ~3 s with sub-ceiling peaks and zero pressure events, while this run stormed ~13 minutes pinned at the ceiling -- the baseline agent's fingerprint; (c) the worker holds no GitHub credential capable of the authenticated artifact download the issue demands.
- Net effect: ~13 minutes of Render time plus four OOM restarts were burned on a run that could never test what the issue asked, and the failure was misattributable to the artifact under test.

## Interpretation

The storm abort is the designed response to a systematic capacity mismatch; the reusable defect is the silent wrong-binary substitution for exact-artifact qualification issues. The issue's own rules ("never silently fall back", download/auth failure is a harness defect) were violated by proceeding without a delivery mechanism. The honest repair is a pre-creation fail-closed gate: refuse the attempt before any Render service exists with a precise infrastructure-blocked diagnostic naming the required artifact and the missing capability. This strictly dominates the status quo on retry (seconds and zero cost instead of ~13 minutes and four restarts, same recovery-loop outcome) and protects every future exact-artifact issue. Landing a real delivery mechanism (credentialed fetch plus payload selection plus worker verification) stays a separate, larger track; the blocker message names the single choke point to update.

## Reusable knowledge

- An exact GitHub Actions artifact cannot execute on the ephemeral Render worker today: the submit-job payload carries no artifact selection, the worker boots with no workflow-artifact identity, and neither the runner nor the credential-scrubbed agent child holds the OAuth/PAT credential the artifact-download endpoint requires. Declare this as infrastructure-blocked, never substitute the baseline binary.
- A 13-minute pinned-at-ceiling replacement storm is the baseline agent's fingerprint; the exact PR #12 (`0.0.0`) artifact instead fast-fails in seconds with sub-ceiling peaks and zero pressure events. Use that contrast to tell wrong-binary storms apart from artifact behavior without guessing.
- Exact-artifact contracts are recognized only by the full conjunction (numeric artifact id + numeric source workflow run + sha256 digest); anything weaker invites false-positive refusals.
- A storm verdict that is a true positive still needs the audit trail (deciding inputs, thresholds, branch) -- run 36495681860 is the live confirmation of the replacements branch predicted in the prior repair.
