# Repair missing low-memory default that thrashed run 36449610030 at the 512 MB ceiling

## Hypothesis / objective

Repair the concrete repository defect behind the Render execution failure for source issue #58 in run 36449610030 (execute=failure, cleanup=success, smoke mode): the production OpenCode workload ran without the validated low-memory default, so its peak sat higher than the best measured configuration. Success evidence: the reusable runner applies `BUN_OPTIONS=--smol` by default on every OpenCode child path, regression tests pin the default and its non-clobbering semantics, and the offline suite passes.

## Preconditions / changed premise

Material premise since the issue #73 repair: run 36449610030 is the first live run to exercise the gap-tolerant storm breaker (base commit `1f310c1`, the issue #73 repair itself) and the breaker fired exactly as designed -- initial job plus 3 resubmissions, then fail-fast on the 4th proven restart with memory pressure instead of burning the 140-poll budget. Classification, restart proof, pressure detection, and diagnostics are therefore not the defect; the defect is what the workload carried into the storm. Fully offline; no live Render credentials or service used. Source issue #58 was not closed or modified.

## Procedure

1. Inspected run 36449610030 via `gh run view 36449610030 --repo kodmial/runtime-lab --log`: service `srv-dat95dh7lnhs73c58910` created (plan=free, region=oregon), deploy `dep-dat95e17lnhs73c58ac0` live, runner healthy, job `c5f4292f00b2401eab0133e78f8f6981` submitted 16:16:54, lost to 4 proven restarts and resubmitted 3 times (`0703a1fe` / `44cde9ba` / `3673e0b3` at ~2-3 minute intervals, instances `665689915be4 -> 7f19f7c37b34 -> 4198e9348ef3 -> 6c8259d23e7e -> 807ca1247bec`), then fail-fast storm diagnostic on job `3673e0b3defc4f9087a95486fd01403c` at 16:27:47; cleanup verified deletion (HTTP 404).
2. Read the run's memory summary: cgroup limit 512.0 MB, current max 512.0 MB, peak 512.5 MB, Python RSS ~31 MB, swap 0, memory.events deltas all 0, 5 instance ids with 4 restart transitions -- the worker was pinned at the ceiling while the agent ran, matching the systematic ~600 MB vs 512 MB mismatch.
3. Re-verified the platform contract against current official vendor documentation (`https://render.com/docs/free`, fetched 2026-09-29): Free web services are 0.1 CPU / 512 MB, "Render might restart a Free web service at any time", ephemeral filesystem lost on restart/redeploy/spin-down, single instance, no persistent disks. No material contract change.
4. Verified the Bun contract against current official vendor documentation (`https://bun.com/docs/runtime`, `https://bun.com/docs/bundler/executables`): `--smol` reduces memory at a performance cost (small JavaScriptCore heap, more frequent GC), and standalone executables read runtime flags from `BUN_OPTIONS` (analogous to `NODE_OPTIONS`), so `BUN_OPTIONS=--smol` applies to the pinned standalone OpenCode binary with no recompile.
5. Traced the workload gap in current `main`: `default_opencode_env_overrides()` in `automation/opencode_runner.py` carries only confinement settings (`OPENCODE_CONFIG_CONTENT`, `GIT_TERMINAL_PROMPT`, `OPENCODE_DISABLE_SHARE`) and no memory default; no production path sets `BUN_OPTIONS` (only benchmark/qualification harnesses and the `opencode_lowmem_profile` qualification spec do). The unbounded-PIPE half of the old diagnosis is already fixed on current `main` by issue #80 (`SubprocessCommandRunner` routes through disk-backed `run_bounded`), so this repair scopes to the still-missing memory default.
6. Wired the default in as the single canonical source with setdefault semantics on every OpenCode child path, added regression tests, and ran the offline suite.

## Observations

- The failed run behaved exactly as designed by the #71/#73 repairs up to the terminal error: correct fail-fast classification, correct health qualification (healthy at every proven loss), correct restart proof (instance rotation on all 4 losses), correct 3 resubmissions, correct storm abandonment with pressure evidence (pinned at limit plus 4 transitions). The harness is not the defect; the missing low-memory wiring is.
- `BUN_OPTIONS` appears in current `main` only in benchmark/qualification code (`disk_heap_benchmark.py` mode envs, `opencode_lowmem_profile.py`, coding/max-headless qualify harnesses as a labelled A/B arm) -- never on the production worker launch path (`SubprocessCommandRunner.run`, `_run_exact_opencode_attempt`, `JobManager.__init__`).
- After the fix, `echo $BUN_OPTIONS` through the real `SubprocessCommandRunner` prints `--smol` by default and preserves an explicit operator value; `JobManager` init setdefaults the process env the same way.

## Interpretation

The storm breaker converts a systematic capacity mismatch from a 45-minute budget burn into a ~12-minute fail-fast with an actionable diagnostic, but it cannot make an oversized workload fit. The reusable repair is to actually run the best validated configuration: every saved megabyte counts when the agent peak rides the ceiling. `BUN_OPTIONS=--smol` (~40 MB) does not by itself prove 512 MB reliable -- issues #52/#56 already measured that no software default does -- but shipping the storm without the validated default guarantees the worst-case peak on every attempt. Wiring it as a non-clobbering default keeps operator overrides intact while making the production path match the measured best case.

## Decision / result

- `automation/opencode_runner.py`: new `OPENCODE_LOW_MEMORY_ENV_VAR = "BUN_OPTIONS"` / `OPENCODE_LOW_MEMORY_BUN_OPTIONS = "--smol"` constants; `default_opencode_env_overrides()` now includes `BUN_OPTIONS=--smol` (with the #56/run-36449610030 rationale); new `apply_opencode_env_overrides()` setdefault helper that never clobbers explicit operator values.
- `automation/runner_server.py`: `SubprocessCommandRunner.run` applies the canonical overrides to every child env (ordinary path, including `opencode run` via `run_bounded`); `_run_exact_opencode_attempt` applies them before `_assert_clean` (exact path via direct `Popen`); `JobManager.__init__` setdefaults the process env so scrubbed/inherited environments carry the default too.
- `automation/test_opencode_runner.py`: new low-memory override tests (smol present, no-clobber, non-mapping rejection).
- `automation/test_runner_server.py`: new production-path tests (real command-runner child sees `--smol` by default, operator value preserved, manager-init setdefault without clobber).
- `automation/knowledge/topics/render-lifecycle.md`: promoted the low-memory-default rule with this record as evidence; preserved prior history.

## Reusable knowledge

- The canonical OpenCode subprocess defaults live in `opencode_runner.default_opencode_env_overrides()` and must be applied (not duplicated) by the runner: `BUN_OPTIONS=--smol` is a validated harmless default (~40 MB off peak), and explicit operator values always win via setdefault semantics.
- A correctly firing storm breaker does not exonerate the workload: when the breaker fires as designed, the next repair looks at what peak the workload carried into the storm, not at the breaker.
- Child-process capture on current `main` is already disk-backed and bounded (issue #80 `run_bounded`); do not reintroduce a second spooling layer when repairing memory pressure.

## Unresolved questions / next experiment

- Whether the ~600 MB agent peak can be reduced further (smaller model, streaming output, lower parallelism) so smoke stops riding the 512 MB boundary; a larger Render plan remains a cost decision outside automation scope (free-tier guard unchanged).
- Whether a durable out-of-process job store is warranted for jobs needing near the full 45-minute timeout after even one transient restart (shared-budget starvation applies to any resubmission, storm or not).
- Mirror storm handling into the persistent-controller path (`render_controller._poll_job_terminal`), which still has payload-only visibility and no sampler access; deliberately left out of this scoped repair as in prior runs.
