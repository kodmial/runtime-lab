## Observations

- The failed run behaved exactly as designed by the issue #68 repair up to the terminal error: correct fail-fast classification (3 consecutive 404s per loss), correct health qualification (healthy at every proven loss), correct restart proof (instance rotation on all seven losses), correct seven resubmissions. Classification, detection, and diagnostics are not the defect; the absence of a storm breaker is.
- The seven job lifetimes (~20 minutes wall-clock including deploy/health) plus the eighth job's 24+ minutes `running` exactly fill the unchanged 140x20s (46m40s) poll budget: the budget was sized to cover ONE 45-minute job execution plus margin (run 36399649036), never K full executions, so every resubmission shrinks the next attempt's window below the runner's 45-minute timeout (shared-budget starvation).
- Per-container event counters reset on every replacement, so a global first-to-last counter delta can read 0 across a storm (as in run 36434278632); this run's +430,890 max-stall delta is visible only because the final attempt survived 24 minutes on one instance. Pinning plus replacements (not the global delta) is the robust storm signal.
- The breaker would have abandoned this run at the fourth proven loss (~9 minutes, initial submit + 3 resubmissions) instead of burning the full ~45-minute budget.

## Interpretation

Budget-limited resubmission is the right shape for transient restart clusters but the wrong shape for a systematic capacity mismatch: resubmitting the identical ~600 MB payload onto a proven-thrashing 512 MB worker guarantees the next restart, yielding zero forward progress per attempt while also starving the final attempt's execution window. The reusable fix is an evidence-gated circuit breaker, not another count: abandon only when a streak of consecutive proven-restart losses reaches the lifecycle threshold AND live telemetry proves memory pressure (pinned usage plus replacements or a same-instance stall surge). The pressure gate is what avoids the 1 -> 2 -> 3 -> 4 -> 5 -> unlimited treadmill -- transient host-maintenance clusters without pressure evidence keep full budget-limited recovery, and telemetry gaps fail open toward resubmission. Pending polls between losses do not reset the streak (a doomed attempt running is not progress); a model fallback resets it (different model, changed premise).

## Reusable knowledge

- On Free workers with anytime restarts, budget-limited resubmission needs an evidence-gated storm breaker: abandon resubmission when a streak of consecutive proven-restart losses reaches the lifecycle threshold AND live telemetry proves memory pressure; without pressure evidence the streak alone never abandons.
- Pinning plus replacements is the robust pressure signal (usage >= 95% of the cgroup limit plus >= 2 instance transitions); per-container event counters reset on replacement, so stall surges must be measured within same-instance groups, never as a global first-to-last delta.
- Telemetry-gap paths must fail open toward the pre-existing recovery behavior, never toward abandonment; a corrupt streak counter likewise fails open.
- Shell/HTTP storm fakes pre-seed the Actions-side samples file with pressure JSONL (the background sampler only appends gaps, which the detector ignores); hermetic samples-file overrides keep endless-loss tests deterministic.
