# Redirect Bun/JSC anonymous mmap to a disk-backed pool for OpenCode PR #15

## Hypothesis / objective

The memory class `libvmmalloc` did not catch (issue #56: Bun/JavaScriptCore
large anonymous `mmap` allocations, ~0% of the footprint travels libc
malloc-family paths) can be made experimentally file-backed on ordinary
ephemeral disk with an `LD_PRELOAD` mmap interposer, and the exact OpenCode
PR #15 coding workload then runs under 512 MiB / no swap with >= 32 MiB of
real headroom. Success evidence: cheap controls first (C probe,
`--version`/`--help`, smoke, `/proc` maps proof, redirected bytes
materially above malloc-only coverage, no exec/stack/fixed redirects),
then a same-binary A/B (off/on, two trials each) with cgroup/smaps/shim
telemetry and a verdict of useful / insufficient / incompatible.

## Observations

- C probe, private mode: all 27 checks pass (2 MiB RW redirected,
  file-backed in maps, zero-init, writable; small/ro/exec/fixed/file/
  shared-anon stay anonymous; fork CoW preserved; munmaps clean). Stats:
  `redirected_bytes` 2,097,152 with all bypass reasons populated.
- C probe, shared mode: fails exactly `parent-bytes-unchanged-after-fork`
  (child write parent-visible) — the documented MAP_SHARED fork hazard,
  reproduced deterministically. Disabled mode: silent passthrough (only
  the positive-redirection check fails, no stats file, no stderr noise).
- Bun/Zig runtime findings (directly seen): the binary issues most mmaps
  (incl. the 8 GiB Gigacage reservation) via raw syscalls invisible to
  `LD_PRELOAD` (host `--version`: strace 42 mmaps vs shim `intercepted`
  3); it terminates via raw exit (no destructors — the periodic +
  throttled flush design is load-bearing, verified); short `--version`
  exits in <1 s (synchronous first-flush is load-bearing). With a 16 GiB
  pool, one 1 GiB libc RW mapping redirects on `--version`.
- Rebuilt binary: 171,218,400 B, SHA-256
  `d9f930c1e288fc81a4abb12f0dd3974584ab8d28d5587cfd6c979698fe45f0c0`
  (`--version 1.18.33`, `--help` run-only) — 4,096 B off the #134
  fingerprint despite identical source tarball size, build command, bun
  version and build path. Exact #134 binary identity is therefore NOT
  claimed; both A/B arms run this same binary.
- A/B (same binary, verified ceiling `536870912`/`0` in every trial):
  arm A t1 537,964,544 B (513.0 MiB, max 2534, wall 62 s), t2 537,096,192 B
  (512.2 MiB, max 730, 36 s); arm B t1 537,149,440 B (512.3 MiB, max 5803,
  30 s), t2 545,255,424 B (520.0 MiB, max 9652, 60 s). All four: exit 0, `FOO_LIMIT` 10->20
  host-verified, container pytest `2 passed`, swap 0/0, `oom_kill` 0.
- Shim telemetry (arm B): t1 redirected 1,077,936,128 B (2 mappings),

## Interpretation

- The interposer is correct and safe (private mode): eligibility policy
  proven per class by the C probe, fork CoW preserved, MAP_SHARED hazard
  demonstrated and rejected, fail-closed fallbacks everywhere, default
  behaviour unchanged when unconfigured.
- Coverage beats malloc-only by ~1000x (~1.1 GB redirected vs ~1 MB for
  libvmmalloc), and every real coding trial succeeds with no behavioral
  regression — so the mechanism genuinely reaches part of the Bun heap
  through libc.
- It still does not move the cgroup peak: MAP_PRIVATE file pages, once
  dirtied by the JSC GC, carry the same cgroup charge as anonymous
  memory; only never-touched pages stay reclaimable-clean. The workload
  keeps riding the ceiling in both arms (peaks within 8 MB of each
  other). The remaining ceiling classes — the 8 GiB raw-syscall Gigacage
  reservation (structurally invisible to `LD_PRELOAD`) and dirty private
  pages (reclaimable only via MAP_SHARED writeback, rejected for the
  proven fork hazard, or real swap) — bound this design.
- The arm-A peaks reproduce the #134 marginal band (537.1-538.0 MB vs
  537.8 MB t1), corroborating functional equivalence of the rebuilt
  binary despite the 4 KB digest drift.

## Decision / result

Outcome `succeeded` (definitive answer delivered):

- **Technically works but insufficient memory reduction** — the second of
  the three issue-prescribed verdicts. ~1.1 GB becomes file-backed with
  zero regressions, but peaks stay pinned at the 512 MiB ceiling in both
  arms, so there is no headroom for a Render carry-forward.
- Deliverable 6 (Render wiring behind an opt-in flag) is explicitly
  declined on this evidence: nothing useful would transfer.
- Shipped: shim + C probe + Python contract + bench driver + 22 tests +
  A/B JSON + markdown report (paths in Evidence). No production
  integration; the shim stays an opt-in experiment.

## Reusable knowledge

- Bun/Zig binaries bypass libc for most mmaps (raw syscalls) and exit
  via raw exit_group: any `LD_PRELOAD` mmap design must expect single-
  digit interception counts at startup, must flush telemetry
  periodically + synchronously (destructors never run), and must treat
  per-pid stats files as the unit of aggregation (fixed paths collide
  across helper processes).
- `pthread_atfork` post-fork anonymous fallback is the smallest safe
  fork design for bump-pointer file pools; MAP_SHARED file backing breaks
  fork CoW deterministically (locked by test, not by assertion).
- Bun compile output is locally deterministic but not reproducible
  across build environments (identical source tarball size/command/
  toolchain, 4 KiB digest drift): pin binary identity per build, never
  assume a prior run's SHA reproduces.
- Sparse 2 GiB-per-process pool files cost ~72 KB actual disk for
  35 GB apparent: ordinary-ephemeral-disk backing has no disk-pressure
  cost even at process-tree scale.
- MAP_PRIVATE file backing moves smaps classification without moving
  the cgroup peak once pages are dirtied: measure peak + `max` events,
  never file-backed bytes alone, when judging 512 MB fitness.

## Unresolved questions / next experiment

- Whether a larger pool (>= 16 GiB, covering the 8 GiB Gigacage libc
  reservation) changes anything: unlikely to move peak (reservation is
  mostly untouched virtual), so not run; a challenger must state which
  dirtied class it expects to reclaim.
- Whether `BUN_OPTIONS=--smol` stacks with the shim (orthogonal GC
  lever, ~40 MB class per #56): not combined here; candidate follow-up
  only if a Render-track issue needs another ~40 MB candidate.
- Source-level heap reduction (beyond PR #15's mini fold-out) remains
  the only untested direction with headroom potential; allocator/mmap
  interposition is now exhausted twice (malloc-family in #56, direct
  mmap here).
