# Added deterministic lifecycle fault-injection matrix

## Hypothesis / objective

A deterministic offline fault matrix can prove cleanup and single-worker invariants across lifecycle failures without consuming Render resources or waiting for live failures to occur.

## Prior knowledge consulted

The existing direct-controller and temporary harness lifecycle, mandatory verified cleanup rules, same-worker model fallback, duplicate-delivery idempotency, and issue #9 failure history.

## Preconditions / changed premise

This experiment used fakes/mocks only. It intentionally created no live Render service.

## Procedure

Added a lifecycle fault-injection suite that injects failures before and after service-ID acquisition, through deploy, service lookup, health, submission, polling, OpenCode failure/fallback, cleanup, and GitHub write-back. Production error-redaction paths were strengthened where the matrix exposed diagnostic leakage risks.

## Observations

- Attempts create at most one Render service.
- When no service ID is obtained, no destructive cleanup is attempted.
- Once a service ID exists, every tested terminal failure path enters bounded cleanup.
- Preferred-model fallback stays on the same worker.
- Unverified cleanup prevents a successful result and blocks write-back.
- Duplicate delivery/redelivery does not create another worker.
- Cleanup failure paths remain bounded.
- Secret-shaped diagnostic values are redacted.
- The full matrix runs offline in normal CI.

## Interpretation

The main lifecycle invariants can be regression-tested deterministically instead of waiting for expensive or slow live failures.

## Decision / result

Keep the fault matrix as a permanent regression layer alongside live smoke/E2E tests. Live tests prove real integration; the matrix proves failure-path behavior cheaply and repeatably.

## Validation

Issue #28 completed through PR #29 and merge commit `97dee7cb283d7ebe28997651b7ef977809d41d4a`.

## Reusable knowledge

For external-resource orchestration, live happy-path tests and offline failure-path matrices are complementary. A real smoke test should not be the first place cleanup edge cases are discovered.

## Unresolved questions / next experiment

Extend the matrix when new lifecycle phases or external write-back/reconciliation behaviors are introduced.
