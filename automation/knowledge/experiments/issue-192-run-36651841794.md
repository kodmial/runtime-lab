# Fix the storm record loss count disagreeing with its own diagnostic after run 36650750585

## Hypothesis / objective

Repair the concrete repository defect exposed by the Render execution failure for source issue #58 in run 36650750585 (execute=failure, cleanup=success, smoke mode): the worker lost 4 consecutive jobs to proven restarts while pinned at the 512 MB cgroup ceiling and the storm breaker abandoned resubmission exactly as designed -- and the #190 structured terminal record was written and merged correctly for the first time (3 of 4 files uploaded, `memory_telemetry` attached) -- but the new record disagrees with itself: `consecutive_restart_losses=3` while its own `error` text reports "4 consecutive proven worker restarts" and its own `storm_evidence.restart_transitions=4`. The reusable fix makes the losses-named field count total consecutive proven losses including the terminal loss (shell streak + 1) so the numeric field, the diagnostic text, and the evidence transitions agree. Success evidence: the defect is identified from the run's durable artifact (not guessed), the breaker decision and log diagnostic are byte-identical, regression tests pin the counting invariant, and the offline suites pass.

## Interpretation

- Three consecutive live storms at bases differing only by failure-handling (runs `36647809185` log-only vs `36650750585` structured) confirm the execution failure itself is the permanent capacity gap (~600 MB agent vs 512 MB worker, hermetically irreducible by config-only switches), which the qualification chain owns -- not this repair. What this repair CAN fix is the auditability of the durable evidence the capacity verdict rides on.
- A structured record whose numeric field disagrees with its own text and evidence by one forces every future consumer to guess which of the three is authoritative (streak? losses? transitions?). The single-choke-point fix (derive the stored field from the same `streak + 1` the text already uses) removes the ambiguity without touching the breaker decision, the envelope, or any payload.
- Scoping to the helper's stored field keeps the blast radius minimal: `should_abandon_restart_storm` still takes the resubmission streak, the shell still passes the streak, E2E payloads and sibling fail-fast paths are untouched.

## Reusable knowledge

- A losses-named durable field must count losses, not resubmissions: when an abort record carries both a streak-derived count and a text/evidence-derived count, derive the stored field from the same expression as the text (`streak + 1`), or the record disagrees with itself by one and durable consumers cannot tell streak from losses from transitions.
- The storm breaker threshold takes the resubmission streak while the record takes total losses; the two differ by exactly the terminal loss. Keep the conversion inside the single record-building choke point so the shell, the breaker, and the diagnostic never diverge.
- For non-chain smoke storms, 3 of 4 artifact files (result + memory summary + state, no qualification file) is the complete evidence set -- not a gap. The #190 "2 of 4" gap signature specifically meant the result file was missing.
