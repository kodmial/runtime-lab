# Repair transport fail-fast and five-restart job loss for run 36430429432

## Hypothesis / objective

Repair the concrete repository defects that failed Render execution for source issue #9 in run 36430429432 (execute=failure, cleanup=success, smoke mode): after four proven restart losses consumed all four allowed same-worker resubmissions, the fifth runner job died in a transport-error down-window (five consecutive HTTP 502 polls with /health also failing) that the poll loop treated as terminal on the very first failed /health probe. Success evidence: the terminal transport path requires sustained unhealthiness before failing fast, the resubmission bound covers the observed five-restart cluster, regression tests reproduce both failure modes, and the full offline suite passes.

## Observations

- The failed run behaved exactly as designed by the previous repairs up to the terminal error: correct fail-fast classification (3 consecutive 404s per loss), correct health qualification (healthy at every proven loss), correct restart proof (instance rotation on all four losses), correct four resubmissions. Classification, detection, and diagnostics are not the defect; the transport fail-fast gate and the bound are.
- The five job lifetimes plus the final down-window (~13 minutes wall-clock including deploy/health) sit inside the unchanged 140x20s (46m40s) poll budget, so surviving the down-window plus a fifth resubmission would still have had remaining budget to attempt completion.
- A single failed /health probe after five transport errors cannot distinguish "worker dead" from "replacement booting" (~60s spin-up per vendor docs); the old gate therefore conflated a recoverable mid-restart down-window with a dead worker and wasted the remaining budget.
- The resubmission branch, counters, baseline carry-forward, in-flight (fallback-aware) payload tracking, and diagnostics are all parameterized by the lifecycle constants, so both changes needed shell-branch edits only in the transport path plus comment updates.

## Interpretation

Fail-fast on the first failed health probe converts a transient restart down-window into a terminal failure even though the worker usually answers again inside the budget; requiring three consecutive failed probes (15 consecutive transport errors) keeps genuine dead-worker detection (~5 minutes, still far short of the full budget) while letting replacements boot. Separately, Free-worker restarts observably cluster in fives (four proven 404 losses plus a transport down-window that is effectively a fifth restart, with live cgroup evidence pinning memory pressure as the driver), so the reusable fix is a fifth bounded same-worker resubmission of the reproducible payload: quintuple-restart clusters become retries, a sixth consecutive loss still fails fast, and every existing invariant holds (one service per attempt, same-worker policy, unchanged 140-iteration budget, mandatory verified cleanup). A fixed bound of five was chosen over budget-limited resubmission to keep this repair scoped; the treadmill question stays open below.

## Reusable knowledge

- On Free workers with anytime restarts, a single failed /health probe after a handful of transport errors is only proof of a transient down-window: fail fast on transport errors only after sustained consecutive failed probes (3 probes x 5 polls = 15 consecutive errors, ~5 minutes), and reset the streak on any healthy probe or any poll that reaches the worker.
- On Free workers with anytime restarts and in-memory job stores, four retries are insufficient when restarts cluster in fives: allow five bounded same-worker resubmissions (six job attempts total) within the unchanged poll budget, and keep failing fast on the sixth consecutive loss.
- Parameterize retry branches by lifecycle constants so bound changes need no shell-logic edit; shell/HTTP fakes for consecutive losses must rotate a fresh instance id per loss, including one past the old bound, or the final loss reads as "same worker process lifetime" and weakens the regression.
- Live cgroup telemetry (limit/current/peak pinned at 512 MB with Python RSS ~32 MB and memory.events max movement) discriminates OOM/resource-pressure restarts from host maintenance; keep the observer on the Actions side so pre-restart samples survive.

## Unresolved questions / next experiment

- Whether five resubmissions suffice for even larger clusters (six or more consecutive restarts in one attempt); the resubmit counter plus instance-rotation evidence in the diagnostics will answer from live runs.
- The fixed resubmission bound keeps growing one live failure at a time (1 -> 2 -> 3 -> 4 -> 5); if six-loss clusters are ever observed, prefer the budget-limited resubmission (retry while poll budget remains) or a durable out-of-process job store suggested in the issue #60 record instead of another fixed-bound increment.
- Whether the ~600 MB agent peak can be reduced (smaller model, streaming output, lower parallelism) so smoke stops riding the 512 MB boundary; a larger Render plan remains a cost decision outside automation scope (free-tier guard unchanged).
- Mirror loss handling into the persistent-controller path (`render_controller._poll_job_terminal`), which still has payload-only visibility; deliberately left out of this scoped repair as in prior runs.
