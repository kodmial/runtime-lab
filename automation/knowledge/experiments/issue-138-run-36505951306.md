## Observations

- The failed run behaved exactly as designed at the gate: the pre-creation check detected the full conjunction (numeric artifact id + numeric source workflow run + sha256 digest) in #110's phrasing, refused before any Render API creation call with advisory plus superseded redirect, and cleanup correctly found nothing to delete.
- Minting repair #138 was correct envelope behavior, not a defect: this was the first-ever posted fingerprint for this failure mode (`SAME_FAILURE_COUNT=0`), so the dedup branch could not fire. The next identical redispatch will take the "Repeated identical..." branch (no new repair, qualification chain triggered) -- provided its fingerprint still matches, which the fix below guarantees.
- The reusable gap: the durable `render-qualification-110-36505913972` payload (classification infrastructure/subtype identity, fingerprint `17aee62a...`) carries no `permanent`/`superseded`/`successor` fields, so the qualification comment, the dedup marker context, and the qualification-chain router cannot distinguish "retired forever, redirect to the successor" from "blocked until a delivery mechanism lands" without re-scraping log text. The #133 fix added those fields to the refusal record but not to the classifier output that downstream automation consumes.
- After the fix, the same live-shaped inputs produce the same classification (`infrastructure`/`identity`), the same fingerprint (`17aee62a...`, byte-identical to the posted marker), plus `permanent=True`, `superseded=True`, and the full successor mapping (`11004835952`/`36498663107`/`1.18.33`).

## Interpretation

The execute=failure outcome for run 36505913972 is the gate working correctly at HEAD, not a lifecycle defect: storm detection, resubmission, polling envelope, and cleanup never engaged because no worker could honestly test what #110 requires. The reusable defect class -- silent wrong-binary substitution for exact-artifact qualification issues -- stays repaired, and the retirement redirect from #133 stays intact. The gap this run exposed is retirement visibility in the durable qualification record: the refusal file knows the contract is retired, but the classifier that feeds triage/dedup/chain drops that knowledge. The honest repair is to propagate the three retirement fields at the single classifier choke point while freezing the fingerprint inputs, so the already-posted marker keeps deduping instead of being invalidated by the very fix that improves the payload.

## Decision / result

- `automation/record_render_qualification.py`: new garbage-safe `refusal_retirement(result)` helper (returns `permanent`, `superseded`, `successor`, coerced; unparsable input means no signal, never a classification failure); `classify` attaches the three fields to the payload AFTER computing the fingerprint on the unchanged field set, with the stability rationale documented inline.
- `automation/test_record_render_qualification.py` (new, 6 tests): retired #110-shaped refusal keeps infrastructure/identity plus `permanent`/`superseded`/successor IDs; fingerprint equals the live posted marker `17aee62a...`; adding the retirement fields to a refusal provably does not change the fingerprint; ordinary empty and non-superseded refusals carry no signal; the helper is garbage-safe.
