# Repair job loss on transient Free-worker restart via one same-worker resubmission

## Hypothesis / objective

Repair the concrete defect that failed Render execution for source issue #9 in run 36409152332 (execute=failure, cleanup=success, smoke mode): a submitted runner job polled as pending for ~2 minutes, then turned into a permanent unknown-job 404 while the runner stayed healthy. The poll loop from the run 36402447309 repair correctly failed fast, but the attempt still failed with no recovery even though the submit payload is fully reproducible and the worker was healthy again.

## Prior knowledge consulted

- `automation/knowledge/PROTOCOL.md` (READ -> PLAN -> EXECUTE -> RECORD -> PROMOTE).
- `automation/knowledge/topics/render-lifecycle.md` (one worker per attempt, 140x20s poll envelope, in-memory job store with fail-fast unknown-job classification, no second service for fallback/retry).
- `automation/knowledge/topics/agent-execution.md` and `scheduler-recovery.md` (repair must fix reusable implementation with regression coverage, not repeat the failed experiment).
- `automation/knowledge/experiments/issue-9-run-36379129913.md` (owner.id contract), `issue-9-run-36399649036.md` (poll envelope must cover the 45-minute runner timeout), and `issue-31-run-36408413138.md` (poll classification: empty is not evidence of work; persistent 404/410 fails fast; in-memory job store plus restartable workers).
- `automation/knowledge/experiments/issue-27-run-36405661952.md` and `issue-28-run-36405666089.md` (watchdog and fault matrix; this repair stays in the job-poll path, not cleanup).

## Preconditions / changed premise

Material premise changed since the run 36402447309 repair (issue #31): the poll budget is sufficient (140x20s) and poll-outcome classification works as designed -- run 36409152332 proves it, failing fast after 3 consecutive 404s instead of waiting out the budget. The remaining defect is not classification but the absence of any recovery: one transient worker restart deterministically fails the whole attempt. No live Render credentials were used; the fix was developed and verified offline with contract-level fakes. Source issue #9 was not closed or modified.

## Procedure

1. Inspected run 36409152332 via `gh run view 36409152332 --repo kodmial/runtime-lab --log`: service `srv-dat3v260tbcc739pkthg` created, deploy `dep-dat3v2m0tbcc739pkvng` live, runner healthy, job `65992564784b4e398e356a278e74615b` submitted at 10:21:59, then `Runner no longer knows job ... (HTTP 404 on 3 consecutive polls; runner health: healthy)` at 10:24:41 (~162s later, ~8 polls: pending first, then permanent 404). Cleanup verified deletion (HTTP 404).
2. Read `automation/render-job.sh` poll loop, `automation/render_lifecycle.py` poll constants, and `automation/runner_server.py` job store (`JobManager._jobs` in-process dict; `GET /v1/jobs/{id}` returns 404 `unknown job`; `/health` reports `uptime_seconds` and job counts).
3. Verified the platform contract against current official vendor documentation (`https://render.com/docs/free`): "Render might restart a Free web service at any time"; Free web services have an ephemeral filesystem lost on redeploy/restart/spin-down; Free plan is 0.1 CPU / 512 MB; spin-down applies only after 15 minutes without inbound traffic (not this run -- the job was polled every 20s). Disk persistence therefore cannot survive the very event that loses the job; only the controller, which owns the reproducible payload, can recover.
4. Added `JOB_POLL_MAX_JOB_RESUBMITS = 1`, `should_resubmit_after_job_loss()`, and `detect_worker_restart()` (submit-time vs loss-time `/health` uptime comparison) to `automation/render_lifecycle.py`, plus the `RENDER_DOC_FREE_TIER` doc reference.
5. Extended the `automation/render-job.sh` poll loop: on the unknown-job threshold with a healthy runner, resubmit the identical payload once on the SAME worker (new job id, counters reset, same overall 140-iteration budget; never a second Render service), with restart evidence in the diagnostic; a second consecutive loss still fails fast. Also fixed the model-fallback path to track the in-flight payload so a later resubmission retries the fallback model.
6. Added regression tests and ran the full offline suite.

## Observations

- The failed run's poll loop behaved exactly as designed by the previous repair: silent pending polls for ~2 minutes, then fail-fast on 3 consecutive 404s with a health-qualified diagnostic. Classification is not the defect.
- The worker was healthy at loss time, so the job id died while the service lived -- the signature of a worker process restart (documented anytime-restart on Free) wiping the in-memory job store, followed by a fresh process answering `/health` 200 with zero jobs.
- The runner's own `/health` already exposes `uptime_seconds`, giving a cheap restart discriminator the previous repair lacked (its record notes the worker-side fate "cannot be determined post hoc").
- The controller-side future path (`render_controller._poll_job_terminal`) has no HTTP-status visibility (its `RunnerJobClient.get_result` returns only a payload mapping), so the same resubmission policy cannot be mirrored there without an interface change; it is recorded below as follow-up, not silently fixed.

## Interpretation

Fail-fast alone converts a diagnosable failure into a fast failure, but on Free workers a single transient restart is routine platform behavior, not an exceptional bug. The reusable fix is bounded tolerance at the poll site: one same-worker resubmission of the reproducible payload, preserving every existing invariant (one service per attempt, same-worker fallback policy, bounded retries, mandatory cleanup, unchanged poll budget).

## Decision / result

- `automation/render_lifecycle.py`: new `JOB_POLL_MAX_JOB_RESUBMITS = 1` with `should_resubmit_after_job_loss()`; new `detect_worker_restart()` uptime discriminator; new `RENDER_DOC_FREE_TIER` doc reference included in `RENDER_DOC_URLS`.
- `automation/render-job.sh`: submit-time `/health` snapshot (best-effort baseline); unknown-job threshold branch now resubmits once on the same worker when healthy (new job id, counters reset, budget unchanged) and otherwise fails fast with both-job-ids, resubmit count, and restart evidence; model-fallback submit now updates the tracked in-flight payload.
- Poll budget, one-service-per-attempt invariant, same-worker model fallback, and mandatory cleanup are unchanged.

## Reusable knowledge

- On restartable workers with in-memory job stores, fail-fast on proven loss is necessary but not sufficient: pair it with one bounded same-worker resubmission of the reproducible payload so a transient restart becomes a retry, not a failed attempt.
- A `/health` uptime clock turns "job gone, runner healthy" from an ambiguous signal into restart evidence: capture it at submit and compare at loss time.
- Disk persistence is not a recovery strategy on workers whose filesystem is documented ephemeral across the same restart event; recover from the side that owns the reproducible input.

## Unresolved questions / next experiment

- Mirror the resubmission policy in the persistent-controller path (`render_controller._poll_job_terminal`): it needs HTTP-status visibility first (currently payload-only), which is an interface change across its fakes and fault matrix -- deliberately left out of this scoped repair.
- Whether one resubmit is enough in practice, or whether Free-worker restarts cluster (e.g. repeated OOM on the 512 MB free plan under the OpenCode workload): the resubmit counter and restart evidence in the new diagnostics will answer this from the next live runs.
- The actual worker-side cause of this specific restart (OOM vs host maintenance) cannot be determined post hoc; the ephemeral service is deleted and Render free-tier services expose no post-mortem API to this repo.
