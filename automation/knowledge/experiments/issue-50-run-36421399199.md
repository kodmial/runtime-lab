# Repair Render smoke failure caused by unpinned OpenCode installer lookup

## Hypothesis / objective

Repair the concrete defect that failed Render smoke execution for source issue #9 in run 36421205678 (execute=failure, cleanup=success), with a reusable fix plus regression coverage.

## Prior knowledge consulted

- `automation/knowledge/PROTOCOL.md` (READ -> PLAN -> EXECUTE -> RECORD -> PROMOTE; catalog-first discovery).
- `automation/knowledge/topics/render-lifecycle.md`, `agent-execution.md`, `scheduler-recovery.md` (no prior record covers installer version-discovery failure).
- `automation/knowledge/experiments/issue-9-run-36379129913.md` (owner.id parsing) and `issue-9-run-36399649036.md` (timeout mismatch): different failure modes, not repeated here.
- Derived catalog queries for issue 9, issue 50, and install/provision history: no previous experiment attempted an installer-version fix, so this is a new failure mode, not a repeated experiment.

## Preconditions / changed premise

Failed run 36421205678 reached deploy-live, runner-healthy, and job-submitted, then failed on a first-seen boundary: lazy OpenCode CLI provisioning inside the worker. No code change since the base commit addresses this path.

## Procedure

1. Pulled the failed-run log (`gh run view 36421205678 --repo kodmial/runtime-lab --log`) and isolated the terminal error.
2. Fetched the live upstream installer (`curl -fsSL https://opencode.ai/install`) and read its version-resolution branches.
3. Checked the official vendor install documentation for supported install forms.
4. Resolved the current release via `gh api repos/anomalyco/opencode/releases/latest` and confirmed the pinned version's tag page and linux x64/arm64 assets.
5. Implemented the reusable fix, added regression tests, and ran the offline suite.

## Observations

- Terminal error in run 36421205678: `Runner job 195cf90a8ab44bff97811e03edec03fb ended with status 'failed': opencode install failed (code 1): Failed to fetch version information; provision via automation/install-opencode.sh (curl -fsSL https://opencode.ai/install | bash)`.
- The upstream installer resolves "latest" with `curl -s https://api.github.com/repos/anomalyco/opencode/releases/latest | sed -n 's/.*"tag_name": *"v\([^"]*\)".*/\1/p'` and exits 1 with `Failed to fetch version information` when the result is empty. `curl -s` hides HTTP errors, so an unauthenticated rate-limit (60 req/hour per IP, shared Render egress) or any transient failure deterministically kills provisioning.
- The installer documents `bash -s -- --version <version>`, and its versioned branch skips the `api.github.com` lookup entirely (only HEAD-checks the release tag page, then downloads the pinned asset).
- Official docs (`https://opencode.ai/docs/`) list the install script, `npm install -g opencode-ai`, Homebrew, and release binaries as supported forms; the pinned install-script form stays within the documented contract.
- Live release check 2026-09-28: latest tag is `v1.18.33` (published 2026-09-28T04:22:46Z) with `opencode-linux-x64.tar.gz`, `opencode-linux-arm64.tar.gz` (plus musl/baseline variants); tag page returns HTTP 200.
- Both provisioning paths used the unpinned form: `automation/install-opencode.sh` (Render build step) and `JobManager._ensure_opencode_binary` (lazy runtime provisioning in `automation/runner_server.py`).

## Interpretation

The worker was healthy and the job payload was valid; the failure is a repository defect in reusable provisioning code, not a transient to be retried blindly. The unpinned installer couples every worker boot to an unauthenticated, unretryable-inside-the-script GitHub API lookup from shared Render egress IPs. Pinning `--version` removes that coupling for both the build-time and lazy runtime paths.

## Decision / result

- Pinned OpenCode provisioning to release `1.18.33` (override via `$OPENCODE_VERSION`):
  - `automation/opencode_runner.py`: new `OPENCODE_PINNED_VERSION`, `OPENCODE_VERSION_ENV_VAR`, `OPENCODE_INSTALL_RETRY_DELAYS=(5.0, 10.0)`; new `resolve_opencode_version()` (env override else pin; strict `X.Y.Z`, strips leading `v`) and `build_opencode_install_command()` (pinned by default, `""` selects the legacy unpinned form); `opencode_install_shell_snippet()` returns the pinned form by default.
  - `automation/runner_server.py`: `_ensure_opencode_binary` provisions with the pinned command and sleeps with bounded backoff between attempts (capped by remaining job budget, none after the final attempt) via `_sleep_between_install_attempts`.
  - `automation/install-opencode.sh`: honors `$OPENCODE_VERSION` (default `1.18.33`) and invokes `bash -s -- --version "$OPENCODE_VERSION"`.
  - Docstrings in `opencode_runner.py`, `runner_server.py`, and `render_lifecycle.py` updated to the pinned pattern.
- Regression tests in `automation/test_opencode_runner.py`: pinned-snippet/command assertions, version resolution/validation (including env override and rejection of non-release strings), env-override install command, lazy-provisioning retry-after-`Failed to fetch version information` with pinned invocations, and install-backoff timing (sleeps only between attempts, capped by budget). The pre-existing provisioning-failure test now zeroes the backoff to stay fast.

## Reusable knowledge

- Never provision workers through an unpinned `https://opencode.ai/install | bash`: without `--version` the script depends on an unauthenticated `api.github.com` latest-release lookup that fails closed ("Failed to fetch version information") under shared-egress rate limiting.
- Prefer explicit `--version <pinned>` for deterministic worker builds; keep the pin current by re-verifying tag plus platform assets, and allow `$OPENCODE_VERSION` override.
- Bounded retries need backoff with a budget cap on small workers; sleeps must be injectable/zeroable so unit tests stay fast.

## Unresolved questions / next experiment

If the pinned asset ever 404s (release yanked), the failure signature will be `Release vX not found` / download 404, not the version-lookup error, and the fix is to re-pin to a current verified release.
