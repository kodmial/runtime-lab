# Bound OpenCode session history and tool-output memory

## Hypothesis / objective
Transient OpenCode memory spikes during one-shot coding jobs come from unbounded session history, shell/test output, tool results, and stale cross-issue state. A fresh-session-by-default discipline plus safe configurable bounds (head+tail diagnostic context with a file-backed retrieval path), bounded streaming/spooling instead of unbounded strings, and compaction/filtering before load can cap every tool call and every accumulation without hiding critical errors or changing provider semantics, independently benchmarkable against the issue-52 baseline.

## Interpretation
The equality-matching miss confirms why bound tests must use duplicate-content fixtures: real tool output is highly repetitive (30 identical 5 kB results), and any set-membership check on content silently defeats the cap. The modest 13.8% stress reduction is expected and honest: with default caps, s3's 50x20 kB calls (≈1 MB) sit near the 1 MiB session budget by design, so the win at this layer is the hard cap (no call or accumulation can exceed it) rather than a large byte saving — the RSS win must come from the fork binary actually enforcing these bounds on the Bun/anon-mmap path (#56 finding), measured by the resourced builder. The head+tail + spool design is what makes the cap safe: the pre-existing `truncate` kept head only, so tail errors were the first casualty of large logs.

## Reusable knowledge
- Bounded-capture pattern: every tool/shell output goes through a spool with three numbers (memory cap, disk-spill threshold, head fraction); the agent sees only the bounded head+tail snapshot and retrieves more only through bounded file windows — never by loading the full string.
- Head+tail, never head-only: truncation must preserve the tail (where errors surface) plus a marker with the elided count and spool path; the old head-only cut is what hid failures in large logs.
- Compaction-before-load: truncate each message first, then keep errors plus newest under both count and byte budgets; match messages by position because real transcripts contain identical duplicates.
- Fresh-session-by-default: isolate the session dir per issue+run, scrub resume variables, and reject resume flags fail-closed; build the command through the existing runner so provider semantics cannot drift.
- Baseline substitution rule (from #79, reapplied): when the fork binary cannot be built in this worker, record the hermetic bounded-vs-unbounded accounting plus the unchanged issue-52 baseline and defer the binary delta to the resourced builder with the same harness — never fabricate it.
