# Wire the remaining qualified low-memory switches after run 36629689414 stormed with only BUN_OPTIONS

## Hypothesis / objective

Repair the concrete repository defect behind the Render execution failure for source issue #58 in run 36629689414 (execute=failure, cleanup=success, smoke mode): the production OpenCode workload ran with only the single `BUN_OPTIONS=--smol` default wired (issue #75 repair) while the remaining validated config-only kill-switches from the qualified issue #78 profile were absent from every production child path, so the worker carried avoidable dead weight (plugin loads, skill discovery, LSP downloader, share uploader, autoupdate check, models catalog fetch, embedded web UI) into a storm it then lost. Success evidence: the canonical overrides carry the full validated set on every child path, regression tests pin presence plus non-clobbering plus profile parity plus frozen argv, and the offline suite passes.

## Observations

- The failed run behaved exactly as designed by the #71/#73/#112/#113 repairs up to the terminal error: correct fail-fast classification, correct health qualification (healthy at every proven loss), correct restart proof (instance rotation on all 4 losses, including the larger-uptime replacement `54.4 -> 60.3` that uptime-order alone would misread), correct 3 same-worker resubmissions, correct storm abandonment with gap-tolerant pressure evidence (pinned at limit plus 4 transitions via the replacements branch despite quiet stall counters).
- `OPENCODE_PURE`, `OPENCODE_DISABLE_DEFAULT_PLUGINS`, `OPENCODE_DISABLE_EXTERNAL_SKILLS`, `OPENCODE_DISABLE_LSP_DOWNLOAD`, `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_MODELS_FETCH`, `OPENCODE_DISABLE_EMBEDDED_WEB_UI` appear in current `main` only in `opencode_lowmem_profile.py`, `opencode_coding_variant.py`, `opencode_direct_headless.py`, and qualification harnesses -- never in `default_opencode_env_overrides()` or any production child env.
- `build_opencode_command` emits exactly `opencode run --auto --model <model> <task>` (asserted by existing tests plus a workflow-parity assertion against `.github/workflows/opencode.yml`, which this token must never modify), so the `--pure` CLI flag cannot be added without breaking that contract; the profile's env half (`OPENCODE_PURE=1`) achieves the same skip with zero argv change.
- After the fix, a real `SubprocessCommandRunner` child sees all seven switches defaulted to `1`/`--smol`, explicit operator values (`OPENCODE_PURE=0`, custom `BUN_OPTIONS`) are preserved, `JobManager.__init__` defaults the full set without clobber, and the emitted overrides equal the issue #78 `STATIC_ENV` on every key production owns.

## Interpretation

- The storm breaker converts a systematic capacity mismatch from a 45-minute budget burn into an ~11-minute fail-fast with an actionable diagnostic, but it cannot make an oversized workload fit. The reusable repair is to actually run the full best validated configuration: the #75 repair shipped one of seven validated switches, leaving the plugin/skill/LSP/share/autoupdate/models-fetch/web-UI side-channels (including npm-install and rate-limited fetcher paths that fail under Render shared egress) active on every attempt.
- These switches are a harmless dead-weight removal by the same standard #75 used: hermetic probes show no startup-peak movement (all arms inside the noise band), the representative coding task passes under them, and setdefault semantics keep operator overrides intact. They are not claimed to close the full ~88 MiB gap between the ~600 MB agent peak and the 512 MB limit on their own; live re-dispatch of #58 must confirm the storm no longer fires.
- Keeping the change env-only (no argv change, no config-file materialization inside the clone, no workflow edits) preserves the read-only-git confinement, the change-detection cleanliness, and the `/proc` cmdline identity evidence by construction.

## Decision / result

- `automation/opencode_runner.py`: new `OPENCODE_PURE_ENV_VAR` / `OPENCODE_PURE_VALUE` plus five `OPENCODE_DISABLE_*` constants in `OPENCODE_LOW_MEMORY_EXTRA_DEFAULTS`; `default_opencode_env_overrides()` now emits the full validated set (with the #78/run-36629689414 rationale); argv intentionally unchanged.
- `automation/runner_server.py`: `JobManager.__init__` defaults the full canonical mapping (replacing the single `BUN_OPTIONS` setdefault); both OpenCode child paths (ordinary command-runner, exact `Popen`) were already covered via `apply_opencode_env_overrides()` and pick the new switches up with no further change; removed the now-unused single-key imports.

## Reusable knowledge

- The canonical OpenCode subprocess defaults live in `opencode_runner.default_opencode_env_overrides()` and must be applied (not duplicated) by the runner; after this repair the set is `BUN_OPTIONS=--smol` plus the six qualified profile kill-switches, all with setdefault semantics so explicit operator values win.
- Pure mode on the production worker arrives via `OPENCODE_PURE=1`, never via a `--pure` argv change: argv order stays identical to the workflow step and to the `/proc` cmdline identity evidence.
- A correctly firing storm breaker does not exonerate the workload: when the breaker fires as designed, the next repair looks at what peak the workload carried into the storm, not at the breaker (reaffirmed for run 36629689414 after the #75 single-switch repair proved insufficient).
