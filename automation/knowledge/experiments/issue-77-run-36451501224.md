# Inventory the OpenCode fork for headless source-level removals

## Hypothesis / objective

Trace the actual `opencode run` startup path in `kodmial/opencode` and
determine exactly what can be disabled by configuration versus what requires
physical source exclusion for a low-memory headless build, while preserving
repo inspection/search, file edits, shell execution, provider calls, the
agent loop, and one-issue session state.

## Prior knowledge consulted

- `automation/knowledge/PROTOCOL.md` (READ -> PLAN -> EXECUTE -> RECORD ->
  PROMOTE lifecycle; catalog-first discovery).
- Catalog queries for issue 76, issue 77, and topic opencode: all empty (no
  prior runs for either issue).
- `automation/knowledge/topics/render-lifecycle.md`: measured worker budget
  (~600-615 MB real agent peak vs 512 MB Free limit), `BUN_OPTIONS=--smol`
  saves only ~40 MB, LD_PRELOAD heap wrappers move 0-1.4% (do-not-repeat),
  pinned OpenCode 1.18.33 provisioning.
- `automation/knowledge/topics/agent-execution.md`: workflow rules (no
  `.github/workflows/**` edits, workflow owns Git state).
- `automation/opencode_runner.py` (non-interactive invocation
  `opencode run --auto --model <model> <prompt>` plus read-only git
  confinement) and `automation/install-opencode.sh` (pinned install).

## Preconditions / changed premise

- Issue #76 (fork bootstrap) is still OPEN, but `kodmial/opencode` `main`

4. Wrote `automation/audits/issue-77-opencode-headless-inventory.md` with the

## Observations

- Default `run` always builds an instance: `run.ts` sets
  `instance: (args) => !args.attach`, and `effect-cmd.ts` routes that through
  `InstanceStore.load` + `InstanceBootstrap.run`, which eagerly runs
  `config.get()`, `plugin.init()`, then `lsp/shareNext/format/vcs/snapshot/
  project` init for every invocation.
- Non-interactive `run` uses an in-process server (`Server.Default().app.
  fetch`, `baseUrl: "http://opencode.internal"`); `Server.listen()` (TCP +
  mDNS) is never used. The interactive footer (`./run/runtime`,
  `footer*.tsx`) is a dynamic import on the interactive branch only.
- `run.ts` permission ruleset denies `question`/`plan_enter`/`plan_exit` in
  non-interactive mode; `--auto` flips permission replies to `"once"`.
- Config-verified kill switches exist for: external plugins (`--pure` /
  `OPENCODE_PURE`), 12 internal auth plugins
  (`OPENCODE_DISABLE_DEFAULT_PLUGINS`), external skills, per-server MCP
  (`mcp.<name>.enabled=false`), LSP (`lsp.<name>.disabled`, empty map,
  `OPENCODE_DISABLE_LSP_DOWNLOAD`), formatters (`formatter:false`,
  per-formatter `disabled`), share (`OPENCODE_DISABLE_SHARE=1`),
  snapshot (`snapshot:false`, partial), autocompact/prune, models fetch,
  provider allowlists (`disabled_providers`/`enabled_providers`), autoupdate.
- Static imports defeat config-only bundle savings: `index.ts` imports all
  ~22 subcommands; `app-runtime.ts` imports ~50 services;
  `httpapi/server.ts` imports the full domain set; `registry.ts` imports all
  16 builtin tools; `plugin/index.ts` imports 12 internal plugins;
  `provider.ts` imports all `@ai-sdk/*` providers.
- Snapshot is the sharpest coupling risk: `session/processor.ts` calls
  `snapshot.track/patch` unconditionally around the LLM stream.

## Interpretation

- Configuration-only changes can suppress most runtime init (plugins, MCP,
  LSP, formatters, share, model-catalog fetch, provider scope) but cannot
  shrink the Bun single binary or skip module parse cost.
- Source-level savings require, in order: lazy subcommand loading
  (`index.ts`), bootstrap laziness (`project/bootstrap.ts` gating),
  registry/route laziness, then dependency pruning (unused providers,
  TUI/web/desktop, MCP SDK, plugin npm-install path).
- No conclusion requires a custom provider/API reimplementation; that stays
  out of scope per the issue.

## Decision / result

- Deliverable committed: `automation/audits/issue-77-opencode-headless-
  inventory.md` (evidence-backed, every claim tied to fork paths at
  `9000e7f` / upstream `ad6c72c`).
- Regression guard: `automation/test_opencode_headless_inventory.py`.
- Definition of Done: initialization traced end to end (index -> effectCmd
  -> AppRuntime -> InstanceStore -> InstanceBootstrap -> run handler ->
  in-process server -> processor); config-only vs source-level savings
  separated; candidates specific enough for a follow-up implementation task
  (file/function-level steps 0-4); provider reimplementation out of scope.

## Reusable knowledge

- `opencode run` (non-interactive, non-attach) always pays
  `InstanceBootstrap.run`: config + plugin + lsp/shareNext/format/vcs/
  snapshot/project init. Cheapest step-0 lever is the §2 flag set, not CLI
  flags (run has no skip-bootstrap flag except `--attach`, which changes
  the execution model).
- Bundle-size levers are all static-import edges: `index.ts` command table,
  `app-runtime.ts` layer graph, `httpapi/server.ts` route imports,
  `tool/registry.ts` builtin imports, `plugin/index.ts` internal plugins.

## Unresolved questions / next experiment

- Whether `snapshot:false` is safe given unconditional
  `snapshot.track/patch` in `session/processor.ts` (needs a harness run or
  a no-op backend, not just config).
- Effect of `OPENCODE_EXPERIMENTAL_DISABLE_FILEWATCHER` on the `run` path.
- Whether `upgrade()` is reachable from `run` (no caller found on the run
  path; verify before claiming savings).
- Step-0 memory numbers: re-run `memory_benchmark.py --include-network`
  with the flag set and Docker 512 MB trials per removal step.
