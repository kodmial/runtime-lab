# Wire the config-file half of the qualified low-memory profile after run 36632841000 stormed with the full env set

## Hypothesis / objective

Repair the concrete repository defect behind the Render execution failure for source issue #58 in run 36632841000 (execute=failure, cleanup=success, smoke mode): the production OpenCode workload ran with the full validated env switch set (issues #75/#159) while the worker config still carried only the permission ruleset, leaving the default MCP/LSP/formatter/share/autoupdate/provider/plugin subsystems active on a 512 MB worker that then pinned at the ceiling and lost 4 consecutive jobs to proven restarts. Success evidence: `OPENCODE_CONFIG_CONTENT` carries the full qualified config equal to `lowmem_config()`, regression tests pin the config keys plus profile parity plus production-child inheritance, and the offline suite passes.

## Observations

## Interpretation

- The storm breaker converts a systematic capacity mismatch from a 45-minute budget burn into a ~13-minute fail-fast with an actionable diagnostic, but it cannot make an oversized workload fit. The reusable repair is to actually run the full best validated configuration: the #159 repair shipped the env half of the profile while the config-file half never reached the worker, leaving default MCP server spawning, LSP servers/downloaders, formatters, share sync, update checks, multi-provider init, and external plugin lists active on every attempt.
- The config-file switches are a harmless dead-weight removal by the same standard #75/#159 used: hermetic probes show no startup-peak movement for the env analogues, the representative coding task passes under the profile, `validate_profile` accepts exactly this triple, and setdefault semantics keep operator overrides intact. They are not claimed to close the full ~88 MiB gap between the ~600 MB agent peak and the 512 MB limit on their own; live re-dispatch of #58 must confirm the storm no longer fires.
- Injecting the config via `OPENCODE_CONFIG_CONTENT` (env, merged last as `local`) rather than writing `opencode.json` into the clone preserves the read-only-git confinement, keeps `git status` change detection clean (no new untracked file inside the checkout), and keeps the `/proc` cmdline identity evidence unchanged by construction.

## Reusable knowledge

- `OPENCODE_CONFIG_CONTENT` is a full OpenCode config document on the production worker (fork `config.ts`: `loadConfig` + `local` merge, highest local precedence), not a permission-only field: the canonical worker config must equal `opencode_lowmem_profile.lowmem_config()` exactly, and parity is regression-locked.
- Prefer env-based config injection over writing `opencode.json` into the job clone: file materialization inside the checkout would surface as untracked changes in `git status` change detection, while the env path keeps detection clean with identical effect.
- A correctly firing storm breaker does not exonerate the workload: when the breaker fires as designed, the next repair looks at what peak the workload carried into the storm, not at the breaker (reaffirmed for run 36632841000 after the #75 single-switch and #159 env-switch repairs both proved insufficient).
