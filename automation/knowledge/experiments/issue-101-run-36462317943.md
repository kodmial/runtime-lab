# Apply real coding-only source stripping and measure the fork binary

## Hypothesis / objective
A real coding-only low-memory OpenCode variant can be implemented as an
additive fork change in `kodmial/opencode` (dedicated headless
entrypoint/build targets whose static-import graph excludes TUI/desktop/
web UI, MCP, LSP/formatter, unused plugins/skills/web tools while
preserving the provider/model/session/agent loop plus repository
read/search, edit/write/patch, shell/build/test, with the full
upstream-compatible build kept usable) and benchmarked as a real Linux
binary: exact fork/base SHA plus binary SHA-256 recorded, process-tree/
cgroup peak measured on the representative coding workload under a real
512 MiB no-swap-equivalent constraint, compared against the ~600-615 MB
baseline and the config-only/bounded/direct-headless tracks, with no
success claimed from `--version` or a fake workload.

## Interpretation
- The patch is a genuine compile-graph separation, not a permission
  sketch: each new file's forbidden imports are enumerated and tested
  (including relative-spelling gaps the first draft missed), the full
  build files are never rewritten, and the no-op snapshot backend plus
  dynamic-only gated imports respect the #77 coupling findings
  (unconditional `track`/`patch`, watcher HEAD subscription, in-process
  fetch mechanism kept).
- The measurements separate signals honestly: `--version` (~191 MB) and
  the deterministic task probe (~8 MB) are recorded as non-success
  baselines; the only agent-memory verdict comes from the live runs
  (615.7 MB host completion vs 512m OOM kill), which reproduce the #52
  baseline family and leave a ~104 MiB gap for the stripped binary to
  close.
- The lite-binary delta is correctly deferred, not claimed: without `bun`
  and without a fork checkout in this worker, compiling `build-lite.ts`
  here is impossible; the patch's build scripts use the same Bun compile
  path so a resourced fork builder can produce the comparable artifact
  and rerun this exact harness per removal group.
- The missing fork PR is an environment/envelope limitation (self-target
  workflow + no-push rule + denied clone), not a patch defect; the
  reviewable appliable change plus the pinned branch name and PR steps
  are the complete handoff the workflow needs.

## Reusable knowledge
- Coding-entry shape that keeps the lite closure minimal: a standalone
  `run-coding.ts` importing only `../../lite/agent` + `../../lite/tools`
  (never `./run`, or the full bootstrap/route graph is dragged back in);
  `tools.ts` re-exporting only the seven real fork tool modules
  (`tool/read|grep|glob|edit|write|apply_patch|shell` — the lite spec's
  `tool/bash`/`tool/patch` shorthand does not exist in the real fork, so
  real-tree checks must use the `shell`/`apply_patch` spellings).
- Boundary patterns must include plain relative spellings (`tui`, `mcp`)
  in addition to path-qualified forms, or `./tui` / `../mcp/mcp` slip
  through while `cli/cmd/tui` / `@/mcp` checks pass.
- Snapshot/watcher safety without importing excluded subsystems: a local
  no-op `track`/`patch` backend plus dynamic-only gated imports keeps the
  processor interface intact with zero excluded edges in the closure.
- Live-model re-baselining is cheap and decisive: one host `opencode run
  --auto` plus one Docker 512m trial classifies the track (here 630,524
  kB completion vs exit-137 OOM) without any Render dependency.
