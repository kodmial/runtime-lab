# Repair double-restart job loss by allowing two same-worker resubmissions

## Hypothesis / objective

Repair the concrete defect that failed Render execution for source issue #9 in run 36417263684 (execute=failure, cleanup=success, smoke mode): both the original runner job and its single allowed same-worker resubmission were lost to consecutive proven worker restarts, so the attempt failed fast with `resubmissions used: 1/1` even though the worker was healthy throughout.

## Preconditions / changed premise

Material premise changed since the issue #33/#41 repairs: run 36417263684 exercised the single-resubmission path and lost BOTH jobs on the same healthy service with direct instance-rotation proof (fe21f53ff840 -> b7c7865bf540 -> 4e9b50b43378; uptimes 11.1 -> 52.5 -> 43.2), at ~6.5 minutes and ~18 minutes after each submit. This falsifies "one transient restart per attempt" as a sufficient bound: the vendor contract permits restarts at any time, and two live runs (36410676408, 36417263684) now show the double-loss cluster signature. The fix targets the resubmission bound only; poll budget, one-service invariant, and mandatory cleanup are unchanged. Fully offline; no live Render credentials or service used. Source issue #9 was not closed or modified.

## Procedure

2. Read `automation/render-job.sh` poll loop, `automation/render_lifecycle.py` (`JOB_POLL_MAX_JOB_RESUBMITS = 1`, `should_resubmit_after_job_loss`, `detect_worker_restart`/`format_restart_evidence`), and `automation/runner_server.py` (in-process job store).
3. Verified the platform contract against current official vendor documentation (`https://render.com/docs/free`, fetched 2026-09-28): "Render might restart a Free web service at any time"; Free web services have an ephemeral filesystem lost on redeploy/restart/spin-down; Free plan is 0.1 CPU / 512 MB; idle spin-down applies only after 15 minutes without inbound traffic (excluded here by 20s polling). Disk persistence therefore still cannot survive the restart event; only the controller, which owns the reproducible payload, can recover.
4. Raised `JOB_POLL_MAX_JOB_RESUBMITS` from 1 to 2 with updated comments citing run 36417263684; `render-job.sh` logic already honors the constant generically (`POLL_RESUBMITS < POLL_MAX_RESUBMITS`, `resubmissions used: X/N`), so only its comments were updated to the new bound.
5. Updated regression tests and ran the full offline suite.

## Observations

- The failed run behaved exactly as designed by the previous repairs: correct fail-fast classification (3 consecutive 404s), correct health qualification (healthy), correct restart proof (instance rotation on both losses), correct single resubmission, then fail-fast on the second consecutive loss. Classification, detection, and diagnostics are not the defect; the bound is.
- The resubmitted job lived ~18 minutes before its loss, so a second resubmission would have had ~22 minutes of the unchanged 140x20s poll budget remaining -- enough for a smoke attempt to plausibly succeed.
- `render-job.sh` needed no logic change: the resubmission branch, counters, baseline carry-forward, in-flight (fallback-aware) payload tracking, and diagnostics are all parameterized by the lifecycle constant.

## Interpretation

Fail-fast plus one retry converts a single transient restart into a recovery, but Free-worker restarts observably cluster (two consecutive proven replacements in ~25 minutes). The reusable fix is a second bounded same-worker resubmission of the reproducible payload: double-restart clusters become retries, a third consecutive loss still fails fast, and every existing invariant holds (one service per attempt, same-worker policy, unchanged 140-iteration budget, mandatory verified cleanup).

## Reusable knowledge

- On Free workers with anytime restarts and in-memory job stores, a single retry is insufficient when restarts cluster: allow two bounded same-worker resubmissions (three job attempts total) within the unchanged poll budget, and keep failing fast on the third consecutive loss.
- Parameterize retry branches by the lifecycle constant so a bound change needs no shell-logic edit and diagnostics stay consistent (`resubmissions used: X/N`).
- Shell/HTTP fakes for consecutive losses must rotate a fresh instance id per loss; reusing the last instance makes the final loss read as "same worker process lifetime" and weakens the regression.

## Unresolved questions / next experiment

- Whether two resubmissions suffice for larger clusters (three or more consecutive restarts in one attempt); the resubmit counter plus instance-rotation evidence in the diagnostics will answer from live runs.
- The worker-side trigger for the two replacements (OOM/resource pressure vs host maintenance) remains unproven; the `/health` resource signals plus per-job identity from issue #41 are the discriminating instruments on the next live #9 attempt.
- Mirror loss handling into the persistent-controller path (`render_controller._poll_job_terminal`), which still has payload-only visibility; deliberately left out of this scoped repair as in prior runs.
