# Config/env low-memory profile for headless OpenCode, measured A/B

## Hypothesis / objective

The maximum reliable memory reduction available from supported
OpenCode/Bun configuration alone (no source changes) can be captured as a
reproducible, independently runnable profile for the runtime-lab coding
workload, with every switch verified against the current fork/source,
measured individually and cumulatively on the shared baseline, and with
memory-breaking switches rejected — so the result is directly comparable
with the parallel source-stripped (#79), bounded-output (#80) and
direct-headless (#89) variants in the #81 matrix.

## Interpretation

- The config-only startup-peak hypothesis is falsified by measurement, not
  assumption: disabled subsystems are already empty/lazy on this path
  (zero MCP/LSP servers by default) while the floor is the Bun runtime +
  static module-graph parse — exactly the #77 prediction that configuration
  cannot shrink the binary/parse cost. `BUN_OPTIONS=--smol` likewise shows
  no startup effect here; its #56 ~40 MB win came from GC pressure under a
  sustained stream this probe never builds.
- The profile is still the correct deliverable: it locks every supportable
  runtime saving (GC mode, no plugin/skill/MCP/LSP/formatter/share/update/
  catalog work, single-provider scope, fresh-session isolation) into
  runnable files with a pinnable fingerprint, and its live-stream effect —
  the only place a config win can still hide — is a live #81 measurement,
  explicitly not inferred here.
- The `OPENCODE_DB` fast-fail was a genuine latent defect in the #80
  session path (runner set the path but never created the parent dir),
  fixed in scope because the profile is un-runnable without it; the
  pass-1 "win" is recorded as a cautionary observation, not deleted.

## Reusable knowledge

- Hermetic bootstrap-probe pattern: `opencode run` with an unknown
  provider fails fast after `InstanceBootstrap`, giving a credential-free,
  network-free process-tree peak for exactly the path config switches act
  on. Reuse `memory_benchmark.run_with_peak` (50 ms poll, N=3, max-of-3)
  so evidence stays comparable.
- Artifact-hygiene rule applied: any dramatic single-arm win must survive
  an stderr-shape comparison against the bare arm before recording; a
  fast-fail short-circuit looks exactly like a memory win on peak meters.
- Live-binary corrections: `share:false` is schema-invalid (use
  `"disabled"`); `OPENCODE_DB` requires a pre-created parent dir (launcher
  owns `mkdir -p`).
- Config-only ceiling (measured): startup floor is Bun runtime + static
  graph parse; per-switch and cumulative deltas are noise on that floor.
