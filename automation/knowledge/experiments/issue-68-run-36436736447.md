# Repair six-restart job loss with budget-limited resubmission for run 36434278632

## Hypothesis / objective

Repair the concrete repository defect that failed Render execution for source issue #9 in run 36434278632 (execute=failure, cleanup=success, smoke mode): the original runner job plus all five allowed same-worker resubmissions were lost to six consecutive proven worker restarts inside the unchanged poll budget, so the attempt failed fast with `resubmissions used: 5/5`. Success evidence: resubmission is budget-limited instead of count-limited (a sixth consecutive restart loss becomes another retry, not a terminal failure), a proven same-process loss fails fast immediately as deterministic, regression tests reproduce both the six-loss recovery and the deterministic-loss fast path, and the full offline suite passes.

## Observations

- The failed run behaved exactly as designed by the previous repairs up to the terminal error: correct fail-fast classification (3 consecutive 404s per loss), correct health qualification (healthy at every proven loss), correct restart proof (instance rotation on all six losses), correct five resubmissions. Classification, detection, and diagnostics are not the defect; the fixed-count bound is.
- The six job lifetimes (~18 minutes wall-clock including deploy/health) sit well inside the unchanged 140x20s (46m40s) poll budget: only ~54 of 140 poll iterations were consumed, so a sixth resubmission would still have had ample budget left.
- An unknown-job 404 proves the poll reached the worker process (a dead worker answers 502/connection-refused, classified as transport_error), so a loss on the SAME healthy process that accepted the job is airtight deterministic-loss evidence -- failing fast there is both correct and faster than the old count-bound behavior.
- The run's memory summary (cgroup limit/current/peak all 512.0 MB, Python RSS ~32 MB, 762 ok / 1049 samples) is consistent with the memory-pressure driver proven by run 36430429432 (memory.events max +434), though its own first/last event counters show delta 0 because per-container counters reset across the six container replacements; delta-0 across restarts does not exonerate memory pressure.

## Interpretation

A fixed resubmission count is the wrong shape for anytime-restart job loss: any fixed N is falsified by the next (N+1)-restart cluster while poll budget demonstrably remains. The reusable fix is budget-limited resubmission of the reproducible payload on the same healthy worker -- restart-driven losses retry while poll iterations remain (the 140-iteration loop bound guarantees termination; each loss costs at least 3 polls, so at most ~46 resubmissions fit), and only an exhausted budget or a proven deterministic loss fails fast. Every existing invariant holds (one service per attempt, same-worker policy, unchanged poll budget, mandatory verified cleanup).

## Reusable knowledge

- On Free workers with anytime restarts and in-memory job stores, a fixed resubmission count is a treadmill: budget-limit retries instead (resubmit the reproducible payload on the same healthy worker while poll iterations remain; the loop bound guarantees termination), and stop only on exhausted budget or proven deterministic loss.
- An unknown-job 404 proves the poll reached the worker, so a healthy same-process loss is deterministic: fail fast immediately instead of burning budget on unrecoverable retries.
- Shell/HTTP fakes for endless-loss scenarios must rotate a fresh instance id per loss past any modeled prefix; reusing the last instance makes later losses read as "same worker process lifetime" and weakens the regression (and now changes the verdict path, not just the diagnostic).
