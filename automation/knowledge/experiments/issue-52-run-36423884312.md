# Benchmark Render worker memory and pin deterministic provisioning

## Hypothesis / objective

Find the lowest-memory reliable architecture for the ephemeral Render worker
(0.1 CPU / 512 MB, no swap) with reproducible GitHub Actions measurements,
then implement the evidence-backed provisioning fix while preserving the
GitHub issue -> worker -> OpenCode -> result contract and all cleanup /
one-service-per-attempt invariants.

## Preconditions / changed premise

New P0 investigation with no prior memory measurements in the repository.
Material premise enabling it: this run executes on GitHub Actions with a
live pinned OpenCode 1.18.33 binary, Docker for cgroup-limit stress, and a
working anonymous free-model path, so real agent peaks are measurable rather
than estimated.

## Procedure

1. Verified upstream/vendor behavior from primary sources: fetched the live
   `https://opencode.ai/install` script (HOME install dir, `--version` /
   `--binary` / `--no-modify-path` branches), read `https://opencode.ai/docs/`
   install forms (script, npm/bun/pnpm/yarn `opencode-ai`, brew, release
   binaries, docker), confirmed the Render Free constraint from
   `https://render.com/docs/free` (free = 0.1 CPU / 512 MB, restart anytime,
   ephemeral filesystem), and inspected the local binary (`file`/`ldd`: ELF
   x86-64, libc-only, ~177 MB; `npm view opencode-ai version` = 1.18.33).
2. Built `automation/memory_benchmark.py` (stdlib-only, rerunnable via
   `--output`/`--report`, `--include-network` gate): full descendant-family
   VmRSS polling, cgroup v2 signals, `/usr/bin/time -v` secondary, variants
   A (Python + subprocess), B (standalone `--version` and live `run`),
   C (npm/Node proxy, Bun availability), D (conditional Go prototype),
   deterministic git-clone proxy, and Docker `--memory=512m
   --memory-swap=512m` no-swap stress with ceiling probe, `--version`
   positive control, synthetic-hog negative control, and live-agent stress.
3. Ran the harness with `--include-network` (run 36423884312) and recorded
   the JSON artifact plus the Markdown report under
   `automation/benchmark-results/`.
4. Implemented deterministic provisioning: repo-relative
   `.opencode-bin/opencode` deploy artifact in `opencode_runner.py` +
   `install-opencode.sh`, `RUNNER_ALLOW_RUNTIME_INSTALL=0` strict mode with
   readiness gating and safe path/version logging in `runner_server.py`, and
   the strict start command in `render_lifecycle.py`.
5. Added `automation/test_opencode_provisioning.py` (13 tests) and ran the
   full offline suite plus `bash -n` and catalog validation.

## Observations

- Standalone binary needs no Node/Bun runtime (Bun-compiled ELF, libc-only).
  npm `opencode-ai@1.18.33` is a 3 kB downloader shim for the same binary;
  `node --version` peaks at ~19 MB (`/usr/bin/time`), so package launch can
  only add memory, never save it. Bun is not installed here.
- Host peaks (process-tree polling): bare Python ~10 MB; live
  `runner_server` process ~22 MB; `git clone --depth 1 file://` proxy ~5 MB;
  variant A (Python + fake agent) ~17 MB tree; `opencode --version` ~177–200 MB;
  real `opencode run --auto --model opencode/muse-spark-1.3-contributor-free`
  "say hi in one word" ~604–615 MB, exit 0, max family 1–2 (no hidden helpers).
- Docker ceiling verified (`memory.max=536870912`, `memory.swap.max=0`).
  Under it: `--version` passes (~124–130 MB cgroup peak, `oom 0`); perl
  700 MB hog OOMs (exit 137, `oom_kill 1`); the real agent is
  nondeterministic at the boundary — trial 1 OOM-killed (`agent_exit=137`,
  `oom_kill 1`), trial 2 throttled through (`agent_exit=0`, peak 536,920,064 B,
  `max 140` events). With swap allowed (`--memory-swap=1g`) the agent passes
  with ~52 MB swapped.
- Python controller overhead is ~22 MB against a ~605 MB agent peak (~4%).
- Full suite: 321 passed (308 pre-existing + 13 new); `bash -n` clean;
  catalog validates at 14 records before this write.

## Interpretation

- The agent binary alone exceeds 512 MB by ~90 MB on a real task, so no
  controller architecture can make the Free worker reliable for real agent
  work; the boundary outcome (OOM vs throttled pass) is nondeterministic.
- Because Python costs ~4% of peak and package shims add a runtime, neither
  a Go rewrite nor an npm/Bun relaunch can fix the overage; both are rejected
  on measured grounds, not preference.
- The build-vs-runtime `$HOME` mismatch and lazy `curl|bash` installs are
  real, fixable memory/reliability costs (installer spike plus the
  run-36421205678 failure class) even though they do not shrink the agent
  peak itself — hence deterministic build-time provisioning with strict
  readiness gating.
- Swap would mask ~52 MB but Render Free guarantees none, so the design must
  not depend on it.

## Decision / result

- Recommendation: keep the minimal Python runner + pinned standalone binary
  (lowest-memory reliable combination available); ship deterministic
  provisioning; state honestly that 512 MB cannot reliably host real agent
  runs (reliable envelope ≈ 730 MB = ~605 MB peak + 128 MB headroom;
  `budget.fits_512m=false`).
- Implemented (contracts preserved, no workflow files touched, no Git
  operations performed):
  - `automation/opencode_runner.py`: `.opencode-bin/opencode` deploy-artifact
    resolution (override > deploy artifact > PATH > HOME),
    `RUNNER_ALLOW_RUNTIME_INSTALL` parsing, `probe_opencode_readiness`.
  - `automation/runner_server.py`: strict no-runtime-install fail-fast,
    readiness gating, `/health` opencode fields, safe startup log.
  - `automation/install-opencode.sh`: build-time copy + verify of the deploy
    artifact plus `--version` proof.
  - `automation/render_lifecycle.py`: default start command
    `RUNNER_ALLOW_RUNTIME_INSTALL=0 python -m automation.runner_server`.
  - `automation/memory_benchmark.py` + `automation/benchmark-results/`
    JSON artifact and Markdown report + `automation/test_opencode_provisioning.py`.

## Reusable knowledge

- Measure the full process tree (descendant-family VmRSS + cgroup
  `memory.peak`/`memory.events` + `/usr/bin/time -v`); parent RSS alone
  understates Bun-compiled single-process agents by nothing but misses
  installer/helper spikes when they exist.
- Never provision Render workers through build-time `$HOME` paths alone;
  copy the binary into a repo-relative deploy artifact and resolve it there first.
- Disable runtime `curl|bash` installation on small workers
  (`RUNNER_ALLOW_RUNTIME_INSTALL=0`) and fail readiness fast; lazy installs
  cost memory/CPU exactly when the worker is most constrained.
- Python controller overhead (~22 MB) is negligible next to a ~600 MB agent;
  do not rewrite the control plane for memory reasons without a measured
  material saving.

## Unresolved questions / next experiment

- Re-run the harness after any OpenCode re-pin (including v2): footprint may change.
- Render-side kernel/cgroup accounting may differ slightly from Actions
  runners; the ~600 MB host peak is the portable signal, not a Render sample.
- Whether larger Render plans are acceptable for real agent work is a cost
  decision outside this investigation (no paid plan was created).
- Swap-enabled comparison was measured once (~52 MB swapped); it is
  documented only to rule swap out as a design basis.
