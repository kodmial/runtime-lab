# Cross-repository task execution and write-back for the OpenCode fork

## Hypothesis / objective
A Runtime Lab issue can explicitly target the allow-listed source repository `kodmial/opencode`, run the coding task against that repository in the ephemeral worker, and materialize an issue-correlated branch/PR there, while the issue, priority, dependency state, experiment record and automation ownership remain in `kodmial/runtime-lab` -- with all cross-repo writes authenticated, scoped, auditable and idempotent, and existing self-target behavior intact.

## Interpretation
The hard-coded self-target assumptions were concentrated in five places (job contract, runner validation, handoff gate, materialization repo/body, controller dispatch) plus the shell harness, so a single small contract module with fail-closed validators at each boundary was sufficient. The placeholder-repo doubles in `test_github_app.py` were the only existing tests encoding the old single-repo assumption; rebinding them to the canonical tracking repo preserves their meaning under the new contract. Letting the App/fake client keep a generic constructor while the controller enforces the binding keeps unit-level write-back tests independent of the allow-list.

## Decision / result
Deliver the complete cross-repository execution path: a Runtime Lab issue declaring `<!-- runtime-lab-target: kodmial/opencode -->` deterministically produces a PR in `kodmial/opencode` on branch `opencode/issue<N>-<suffix>` (N = source issue) whose body links `kodmial/runtime-lab#N`, with pinned base SHA, idempotent retry, scoped credentials never visible to the OpenCode child process, and full evidence in the delivery record. Self-target behavior is unchanged.
