## Interpretation

- The storm breaker converts a systematic capacity mismatch from a 45-minute budget burn into a ~12-minute fail-fast with an actionable diagnostic, but it cannot make an oversized workload fit. With the full profile and the workload budget both wired and still pinned at the ceiling, the reusable repair is the task text's own internal contradiction: a bound that the very next instruction overrides is not a bound. The bounded handoff makes the last word the agent reads also bounded, while catalog-first discovery replaces blind full-record reads.
- This does not claim the bounded handoff alone moves the ~600 MB startup floor under 512 MB; hermetic probes already proved prompt/config-only changes cannot move that floor (Bun runtime plus static module-graph parse). It removes the remaining task-controlled transcript-growth driver and the self-amplifying read loop (each repair grows the topic file the next agent is told to read in full). Whether the residual gap needs a smaller qualified binary (coding-only/direct-headless tracks, still pending fork-CI binary deltas) or a larger worker is owned by the qualification chain, not this repair.
- Scoping to smoke mode keeps the blast radius minimal: E2E issues own their success criteria and their payloads are untouched.

## Reusable knowledge

- A workload bound that a later instruction in the same payload overrides is not a bound: every smoke-task cap must agree with the mode-aware handoff, which is the last numbered instruction the agent reads. Put precedence explicitly in the text ("This bound overrides any broader read scope above").
- `resolve_task_text` remains the single chokepoint both live dispatch paths share (`render-job.sh` shell flow and `render_controller.py`), so task-envelope repairs there cover every dispatch shape; mode-gating keeps E2E payloads untouched.
- Repair-topic notes grow monotonically, so unbounded "read the relevant topics/records" orders are a self-amplifying memory driver on a 512 MB worker: always route agents through catalog-first discovery with an explicit read cap.
- A correctly firing storm breaker does not exonerate the workload: when the breaker fires as designed at a base already carrying all prior repairs, the next repair changes what the workload asks the worker to do (reaffirmed for run 36645592095 after the #75/#159/#164/#170/#176 repairs).
