# Diagnose repeated runner job loss with unambiguous process identity

## Hypothesis / objective
Determine and fix the concrete reason both runner jobs disappeared in workflow run `36410676408` (jobs `158f834032644fe0b2a0dc4c7dacb273` and resubmitted `f2bfd75f94804d09996672dbbf5ecd47` turned into permanent unknown-job 404s while `/health` stayed healthy), instead of adding another blind timeout/retry adjustment, and make the next real #9 attempt unambiguously diagnosable.

- `automation/knowledge/topics/render-lifecycle.md` (one worker per attempt, 140x20s poll envelope, in-memory job store with fail-fast unknown-job classification, one same-worker resubmission on proven loss, mandatory verified cleanup).
- `automation/knowledge/topics/agent-execution.md` and `scheduler-recovery.md` (repair must fix reusable implementation with regression coverage, not repeat a failed experiment).
- `automation/knowledge/experiments/issue-9-run-36379129913.md` (owner.id contract) and `issue-9-run-36399649036.md` (poll envelope must cover the 45-minute runner timeout).
- `automation/knowledge/experiments/issue-31-run-36408413138.md` (poll classification: empty is not evidence of work; persistent 404/410 fails fast; jobs live in worker process memory).
- `automation/knowledge/experiments/issue-33-run-36409578168.md` (one bounded same-worker resubmission for transient Free-worker restart; `/health` uptime discriminator; disk persistence cannot survive the restart event; controller payload-only poll noted as follow-up).
- `automation/runner_server.py` (`JobManager._jobs` in-process dict; `GET /v1/jobs/{id}` returns 404 unknown-job; `/health` reported only `uptime_seconds`), `automation/render-job.sh` (submit-time vs loss-time uptime comparison via `detect_worker_restart`), `automation/render_lifecycle.py` (`build_create_service_payload`: free plan, `numInstances: 1`, start `python -m automation.runner_server`).

## Preconditions / changed premise
Material premise changed since the issue #33 repair: run `36410676408` exercised the resubmission path and lost BOTH the original and the resubmitted job on the same healthy service, and its uptime readings (`25.9 -> 48.9 -> 60.3` over several minutes of wall-clock) falsify the legacy `current_uptime < prior_uptime` restart detector, which reported "same worker process lifetime" merely because the later uptime was greater. This repair therefore targets the detector flaw plus unambiguous process identity, not the poll budget or resubmission bound (both unchanged). Fully offline; no live Render credentials or service used.

## Procedure
1. Compared the issue #41 observed sequence against the runner process model: single `ThreadingHTTPServer` process, jobs only in `JobManager._jobs`, no code path deletes or migrates jobs, `numInstances: 1`, so an unknown-job 404 with a healthy `/health` means the serving process no longer owns that job id.
2. Reconstructed the run `36410676408` timeline arithmetically: prior uptime 25.9s at T0, current uptime 48.9s minutes later implies the serving process started ~49s before the later reading (i.e. well after T0); likewise 48.9 -> 60.3 over minutes implies a second replacement. A replacement process can report a larger uptime than the old snapshot, so uptime order alone cannot prove identity.
3. Checked the remaining hypotheses against the model: multiple routed instances are excluded by `numInstances: 1` with one in-process manager; no internal state-drop bug exists in the submit/poll paths (jobs are only added, never cleared); OOM is plausible on the 0.1 CPU / 512 MB free plan under the clone/install/OpenCode workload but cannot be proven post hoc without instrumentation, so it is treated as unproven rather than assumed.
4. Added a unique `instance_id` (uuid at manager startup) plus `pid`/`started_at` to `JobManager`, exposed them in `GET /health` with lightweight resource signals (`read_resource_diagnostics`: thread counts, VmRSS/VmHWM, load average; stdlib-only, best-effort, never secrets), stamped the identity into every job's metadata and status payload, and serialized OpenCode CLI provisioning behind an install lock to cut peak concurrent-installer pressure.
5. Replaced the uptime-only `detect_worker_restart()` with precedence: changed instance ids prove restart directly; else classic shrinking clock; else wall-clock elapsed exceeding the uptime delta by more than `WORKER_RESTART_WALL_SKEW_TOLERANCE_SECONDS` (60s) proves replacement; else same lifetime; else no evidence. Added `format_restart_evidence()` keeping the established message vocabulary.
6. Updated `automation/render-job.sh` to snapshot instance id plus wall-clock time at submit and at loss, evaluate via `format_restart_evidence()`, and carry the baseline forward across the single same-worker resubmission. Bounds unchanged: one service per attempt, at most one resubmission, unchanged poll budget, mandatory cleanup.
7. Added regression tests and ran the full offline suite.

## Observations
- The old detector had exactly one comparison (`current < prior`); on the issue sequence both comparisons are False (48.9 > 25.9, 60.3 > 48.9), hence the false "same worker process lifetime" message quoted in the issue.
- No runner code path other than process replacement explains two consecutive permanent 404s with a healthy service: the job dict is append-only within a process lifetime, and the 404 contract is exactly the fresh-process answer for an id it never accepted.
- The resubmission in the failed run behaved as designed (same payload, same service, new job id) and was then lost the same way, consistent with two consecutive worker replacements rather than one transient.
- Full offline suite after the fix: 302 passed (was 295), including the new instance-identity, wall-drift, resource-diagnostic, install-lock, and shell end-to-end tests; `bash -n automation/render-job.sh` passes; no `.github/workflows/**` changes.

## Interpretation
The established cause of both disappearances is consecutive worker process restarts/replacements wiping the in-memory job store while the service stayed reachable: proven arithmetically from the wall-clock-vs-uptime drift in run `36410676408` (direct instance-id proof was unavailable because the old runner never exposed one). The reusable defects fixed here are the ambiguous identity signal (no instance id; uptime-order-only inference) and the unserialized heavyweight provisioning path; OOM as the trigger for those restarts remains the leading but unproven hypothesis, now instrumented (instance id + pid + started_at + RSS/threads/load on `/health`, per-job identity) so the next live run distinguishes resource termination from an application-level state-loss bug without another speculative repair.

## Reusable knowledge
- Process identity must be explicit (uuid at startup), never inferred from uptime order: a replacement process can report a larger uptime than the old snapshot.
- When instance ids are unavailable (old data), compare wall-clock elapsed against the uptime delta with a jitter tolerance; minutes elapsed with seconds of uptime advance proves replacement.
- On small free workers, serialize heavyweight provisioning (one installer at a time) while keeping job workspaces concurrent and isolated.
- Lightweight `/health` resource signals (RSS, threads, load) plus per-job identity turn the next "job gone, runner healthy" event from ambiguous into discriminating evidence.

## Unresolved questions / next experiment
- The trigger for the two replacements in run `36410676408` (OOM/resource pressure vs host maintenance) is still unproven; the next live #9 attempt with this instrumentation should record `/health` identity plus resource signals at submit, during polls, and at loss to decide it.
- Whether one resubmission suffices when restarts cluster (two consecutive losses failed fast here by design); the resubmit counter plus instance-rotation evidence will answer from live runs.
- Mirror instance-aware loss handling into the persistent-controller path (`render_controller._poll_job_terminal`), which still has payload-only visibility; deliberately left out of this scoped repair as in run 36409152332.
