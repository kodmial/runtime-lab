# Fix the stale issue attribution in the durable memory summary after run 36652760209

## Hypothesis / objective

Repair the concrete repository defect evidenced by the Render execution failure for source issue #58 in run 36652760209 (execute=failure, cleanup=success, smoke mode): the worker lost 4 consecutive jobs to proven restarts while pinned at the 512 MB cgroup ceiling and the storm breaker abandoned resubmission exactly as designed with a correct structured record -- but the durable human-readable memory summary printed in the Actions log misattributes the telemetry as "Container memory summary (issue #57):" for an issue #58 run. The reusable fix makes the sampler header generic so evidence from any issue is attributed correctly. Success evidence: the execution root cause is identified from run evidence (not guessed), the breaker/record path is verified unchanged and correct, the header defect is fixed at its single choke point with regression coverage, and the offline suites pass.

## Interpretation

- Four consecutive live storms at bases differing only by failure-handling (runs `36650750585` vs `36652760209`: same 4-loss cadence, same pinned 1.0, same 5-instance rotation, same ~33 MB Python RSS, differing only by the #192 counting fix) confirm the execution failure itself is the permanent capacity gap (~600 MB agent vs 512 MB worker, hermetically irreducible by config-only switches), which the qualification chain owns -- not this repair. What this repair CAN fix is the auditability of the durable evidence the capacity verdict rides on.
- A durable log header that names the wrong issue forces every future triage to second-guess which run the telemetry belongs to (#57 vs #58 vs any future consumer of the shared sampler). The single-choke-point fix (one literal in `render_human_summary`, the only log-visible attribution) removes the ambiguity without touching the breaker decision, the record shape, the envelope, or any payload.
- Scoping to the header keeps the blast radius minimal: machine-readable summaries carry no issue field and are unchanged, E2E payloads and sibling fail-fast paths are untouched, and module/docstring historical references to the originating issue #57 remain as history.

## Reusable knowledge

- Durable log headers must never hardcode the originating issue number when the module is reused across issues: the shared sampler serves #57, #58, and every future consumer through the same EXIT-trap path, so a fixed `(issue #N)` header misattributes all later runs. Keep human headers generic; carry run identity in structured fields (filenames, result metadata) instead.
- A correctly firing breaker plus a correct structured record does not imply correct human evidence: when a live run validates the prior repair (here #192 field==4==transitions), audit the rest of the same terminal output (log lines, headers, counts) for stale literals before declaring the evidence path clean.
- For non-chain smoke storms, 3 of 4 artifact files (result + memory summary + state, no qualification file) remains the complete evidence set -- not a gap.

## Unresolved questions / next experiment

- Sibling fail-fast poll paths (same-process deterministic loss, budget-exhausted unknown-job loss, sustained transport unhealthiness) still exit log-only; deliberately left out of this scoped repair -- extend with the same helper only if a live run evidences triage pain there.
