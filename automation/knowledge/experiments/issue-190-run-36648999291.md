## Interpretation

- Two consecutive live storms at bases differing ONLY by the handoff bound (runs `36645592095` vs `36647809185`: same 4-loss cadence, same pinned 1.0, same 5-instance rotation, same ~33 MB Python RSS) falsify prompt/handoff scope as the driver for this failure mode. The residual is the binary startup floor itself (~600 MB agent vs 512 MB worker, hermetically irreducible by config-only switches), which no task-text repair can move -- the qualification chain owns the smaller-binary question, not this repair.
- What this repair CAN fix is the cost of learning that again: a log-only storm abort forces every future triage to scrape text and drops the memory merge, while a structured record makes the permanent capacity verdict (`storm=true` plus deciding inputs) durable, upload-complete, and mergeable. This mirrors the #125 refusal-record and #165 hold-verdict repairs for the gate paths.
- Scoping to the storm-abort branch keeps the blast radius minimal: sibling fail-fast paths, the breaker thresholds, the poll envelope, and E2E payloads are untouched.

## Reusable knowledge

- A correctly firing storm breaker does not imply durable evidence: every terminal abort path must persist a structured result record (status plus deciding inputs) to `$RENDER_RESULT_FILE`, or the upload is incomplete and the EXIT-trap memory merge is silently skipped. Log lines are not durable evidence.
- When two consecutive live runs storm identically across a task-text-only diff, the task text is falsified as the driver: do not tighten prompt/handoff bounds a third time; fix the failure handling (or change what runs, e.g. a smaller qualified binary) instead.
- The canonical low-memory profile is verified applied on all three worker spawn paths (manager `setdefault`, ordinary command-runner, exact `Popen`); a ceiling storm at a base containing it is not a wiring regression.
